# CR-012: Error.code 沒有寫進 contract,於是每條 AC 各自釘一次

- **提出者**: qa
- **狀態**: accepted
- **阻擋任務**: 無

> 不阻擋任何任務。但每多一條驗錯誤回應的 AC,就多一處各自為政的斷言 ——
> 這兩輪(#61、#63)已經各留下一段註解說明「這裡為什麼不敢斷言 code」。

## 問題

`openapi.yaml` 的 `Error` 只保證兩個欄位存在:

```yaml
Error:
  type: object
  required: [code, message]
  properties:
    code: { type: string }
    message: { type: string }
```

**`code` 可以是任何字串。** contract 沒有列舉合法值,也沒有在任何一個回應上
說明「這個 400 會給哪個 code」。實際的約定散落在 AC 裡:

| 回應 | code 被誰釘住 | 值 |
|---|---|---|
| `POST /projects` 400 | AC-002 | `VALIDATION_ERROR` |
| `GET /projects` 400(limit / offset) | AC-012 | `VALIDATION_ERROR` |
| `GET /projects` 400(status) | **沒有人** | — |
| `GET /projects/{id}` 404 | AC-004 | `NOT_FOUND` |
| `PATCH /projects/{id}` 400 | **沒有人** | — |
| `PATCH /projects/{id}` 404 | **沒有人** | — |

最尷尬的是第二、三列:**那是同一個 HTTP 回應**。`GET /projects` 的 400 由
limit、offset、status 共用,前兩個參數的 code 被 AC-012 釘成 `VALIDATION_ERROR`,
status 那半邊沒有任何地方講。同一個回應兩半採不同標準。

這跟 TASK-007 自己在抱怨的事情是同一個形狀 —— 那張任務的理由寫著
「同一個 API 裡兩套標準」,而它修的是狀態碼,沒修 code。

## 影響

**不改的話,qa 只剩兩個爛選項,而兩個都不對。**

**選項一:跟著寫 `VALIDATION_ERROR`。** 這是拿測試立法。契約沒說的事由 e2e
單方面決定,backend 挑了別的 code 也不算違規,卻會被我的測試判紅。規則的
真相從 contract 漂到 `e2e/*.spec.ts` —— 而那個檔案只有 qa 寫得到。

**選項二:只斷言形狀(`code` 是非空字串)。** 這是我這兩輪實際採取的做法,
見 `e2e/archive.spec.ts` 與 `e2e/status-filter.spec.ts` 末端的註解。誠實,
但它讓一個回 `code: "E_WHATEVER"` 的實作照樣全綠。client 拿 code 來分支,
這種自由不是好事。

還有第三件事,是我自己的不一致:**`PATCH /projects/{id}` 的 404,我斷言了
`NOT_FOUND`**(`e2e/archive.spec.ts`),理由只是「AC-004 的 GET 404 是這樣」。
那正是選項一。同一份 PR 裡我對 400 守著選項二、對 404 用了選項一 ——
沒有原則能同時支持這兩個決定,只是後者「看起來很明顯」而已。

**看起來很明顯的約定沒有寫下來,就是還沒有約定。**

## 建議變更

兩件一起做,單獨做都不夠:

**一、`Error.code` 加上 `enum`。**

```yaml
Error:
  type: object
  required: [code, message]
  properties:
    code:
      type: string
      enum: [VALIDATION_ERROR, NOT_FOUND]
    message:
      type: string
```

這一步讓約定進到**生成的型別**裡:`components['schemas']['Error']['code']`
從 `string` 變成聯集,e2e 斷言 code 時就是在對契約斷言,不是對慣例斷言。
`check:drift` 也會跟著守住它。

**二、在每個錯誤回應的 `description` 寫明它給哪個 code。**

enum 只說「這個 API 用這兩個 code」,沒說「這個 400 用哪一個」。讀 API 的人
要在回應那裡找得到答案,不必反推。`GET /projects` 的 400 描述已經是三個
參數共用的長段落,補一句「一律 `VALIDATION_ERROR`」是最省的寫法。

建議的對應(全部沿用現況,不新增值):

| 回應 | code |
|---|---|
| 所有 400 | `VALIDATION_ERROR` |
| 所有 404 | `NOT_FOUND` |

**為什麼不留一個 `code: string` 的逃生門。** 日後要加第三個 code(例如
`CONFLICT`),那是一次 contract 變更、一次型別重新生成、一次 CR ——
本來就該被看見。開放的 `string` 讓新 code 可以悄悄長出來,而 client 的
`switch` 不會有人提醒它漏了一個 case。

## 波及範圍

型別重新生成後 `Error['code']` 從 `string` 收斂成聯集,**這是收緊,不是放寬**,
所以要看的是「有沒有人在寫入端用了不在 enum 裡的值」:

- **backend** —— 建構錯誤回應的地方。若 code 是字面量且都在 enum 內,不受影響;
  若是變數(例如 `code: err.name`),會在 `pnpm typecheck` 紅,那正是這張 CR
  想抓的東西。
- **frontend** —— 讀取端。`string` 收斂成聯集對讀取端相容,反而讓
  `switch` 的窮盡檢查開始生效。
- **e2e** —— 我這邊。改完之後 `archive.spec.ts` 與 `status-filter.spec.ts`
  的形狀斷言可以換成對 code 的斷言,末端那兩段註解一併刪掉。這是我的路徑,
  裁決後我送。

`tasks.yaml` 不必改:AC-002 / AC-004 / AC-012 現有的措辭與 enum 一致,
只是從此不再是唯一的來源。要不要把「code 為 VALIDATION_ERROR」從 AC 文字裡
拿掉(避免兩處各講一次)由 architect 決定 —— 我傾向留著,AC 讀起來仍然完整,
而漂移由 contract 那一份守。

## 為什麼由 qa 提出

這是寫測試時才會撞到的缺口:實作端兩邊都用得很自然,只有要**斷言**的人
必須先回答「這件事到底有沒有被規定」。連續兩張 PR 都在同一個問題上留下
「這裡不敢斷言」的註解,就該把它變成一張 CR,而不是第三段註解。

### `enum` 不只是文件 —— 我確認過它會在寫入端變成編譯錯誤

你說「若 code 是變數會在 typecheck 紅」。這件事成不成立取決於 backend 有沒有
真的用生成的型別,我查了:

```ts
backend/src/routes/projects.ts:9
type ApiError = components['schemas']['Error'];
...
(req: Request, res: Response<Project | ApiError>) => {
```

**用了。** 所以 `code` 從 `string` 收斂成聯集之後,寫入端塞一個不在 enum 裡的值
會直接編譯不過,不是等到 e2e 才發現。這讓這張 CR 的價值比它自己宣稱的高一點:
它不只讓 qa 敢斷言,還讓 backend 寫不出違規的值。

現況我也點過:backend 全部十處都是字面量、都在 enum 內,`pnpm typecheck` 綠。
這張 CR 上線不需要任何遷移。

### AC 的文字留著,但它不再是權威

你傾向留著,我同意,理由要說清楚一點:

**AC 講的是「驗收時要看到什麼」,contract 講的是「API 保證什麼」。** 兩者碰巧
是同一個字串,但角色不同。AC-004 讀起來仍然完整,不必要求讀的人先去翻 contract。

代價是同一個事實有兩份拷貝,而 CLAUDE.md 自己說過「抄了就會漂移」。所以補一條
規則:**兩邊不一致時以 contract 為準**,AC 的文字是敘述不是定義。

**我不打算為此做檢查。** 唯一能做的是掃 AC 的散文找 code 樣式的 token 再比對
enum —— 對散文做正規表示式,假警報的成本會超過它擋到的東西。這是一筆刻意留著的
小額欠帳,不是漏看。

### 不留 `code: string` 的逃生門:同意,而且理由比你寫的更硬

你說開放的 `string` 讓新 code 悄悄長出來。再補一點:**這個 repo 的整套設計就是
把「悄悄」變成「吵鬧」。** `check:drift` 抓的是生成物悄悄過期,`check:ac` 抓的是
AC 悄悄失去測試,ADR-003 抓的是依賴邊界悄悄消失。開放的 `code` 是同一個形狀 ——
新增一個值不會讓任何東西變紅,而 client 的 `switch` 沒有人提醒它漏了 case。
enum 讓加值這件事變成一次 contract 變更加一次型別重新生成,那正是應該的重量。

### 我實測撞到的:有一種 400 根本給不出 code

裁決時順手量了錯誤回應的邊界,發現 `Error` 這個 schema 有一條路徑上是假的:

```
POST  /projects       body: {"name":      → 400  content-type: text/html
PATCH /projects/xyz   body: {oops         → 400  content-type: text/html
```

語法錯誤的 JSON 會讓 express 的 body-parser 丟例外,預設錯誤處理器回一個 HTML
頁面。狀態碼對,但 contract 說這個 400 的 content 是 `application/json` 的
`Error` —— **這條路徑上 API 違反自己的契約。**

你這張 CR 讓它更刺眼:一個回 HTML 的回應根本給不出 `code`。所以我開了 **TASK-009
(AC-016)**,contract 不必改 —— 契約本來就是這樣寫的,是實作沒做到。

這也是你那句話的另一個實例:**看起來很明顯的約定沒有寫下來,就是還沒有約定。**
這次是反過來 —— 寫下來了,但沒有人驗過它是不是真的。

### 版本號

`info.version` 維持 `2.1.0`(本 CR 不升版)。收緊**回應**的型別對 client 是相容的方向
(它本來就只會收到這兩個值),對 backend 是編譯期收緊、不是執行期行為改變。
真正會破壞相容的是往 enum 加值之後 client 沒跟上,那時再談升版。
比照 CR-002 裁決的同一條線。
