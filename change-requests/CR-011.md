# CR-011: `verified_by: manual` 要求人工驗收,但沒有欄位記錄它發生過

- **提出者**: infra
- **狀態**: proposed
- **阻擋任務**: 無

> 不阻擋任何任務,但**應該在 TASK-003 進 `done` 之前落地** —— 否則這個制度的
> 第一筆人工驗收,就是沒有紀錄的那一筆,而它正是引出這條規則的那一筆。

## 問題

CR-006 的裁決把 `verified_by: manual` 定義成「由人工驗收」,並且明說:

> `verified_by: manual` 的意思是「由人工驗收」,不是「不必驗收」。

但 `tasks.yaml` 裡沒有任何欄位記錄那次驗收發生過。現有的 `verified_note`
記的是**為什麼自動化測不到**,不是**誰在什麼時候看到了什麼**:

```yaml
- id: AC-005
  text: 顯示名稱、狀態、建立日期
  verified_by: manual
  verified_note: 黑箱 e2e 只 spawn backend 發 HTTP,打不到畫面;見 CR-006
```

`check:ac` 也只驗到這裡:`verified_by: manual` → `verified_note` 非空即可。
一條 AC 可以是 `manual` + 有理由 + 從來沒有人看過,而任務照樣進得了 `done`。

## 影響

**形狀跟 CR-006 抱怨的那件事一模一樣。** 那張 CR 說「frontend 的 done 表示
有人覺得做完了」,裁決把 TASK-003 退回 `review` 以示區別。但在目前的欄位下,
它進 `done` 的依據仍然是口頭的 —— 只是從「有人覺得做完了」變成
「有人說他看過了」。差別比看起來小。

具體場景,而且下週就會發生:`pnpm dev:frontend` 已經做好(#49),使用者看完
AC-005/AC-006 之後告訴 architect,architect 把狀態改成 `done`。三個月後有人問
「AC-006 是誰驗的、什麼時候、看到什麼」,repo 裡沒有答案 —— `git log` 只會
顯示 architect 改了一個 YAML 欄位。

而這種漂移跟 CR-005 講的是同一個方向:**沒有紀錄不會讓任何檢查變紅。**

## 建議變更

欄位屬於 `tasks.yaml`,是 architect 的決定。三條路:

**(a) `acceptance` 加一個驗收紀錄欄位。** 例如:

```yaml
- id: AC-005
  verified_by: manual
  verified_note: 打不到畫面;見 CR-006          # 為什麼自動化測不到
  verified_record:                              # 那次人工驗收
    at: 2026-09-01
    who: zozo0526
    saw: 建一筆後列表顯示名稱、active、2026/9/1
```

`check:ac` 的規則加一條:`status: done` 且 `verified_by: manual` 的 AC,
必須有 `verified_record` 且三個欄位非空。實作是幾行,因為 `check:ac` 已經在
讀這份檔案。**名字不要再用 `verified_by`** —— 那個欄位裝的是「用什麼方法驗」,
跟「誰驗的」是兩件事,共用一個名字會讓兩者都講不清楚。

**(b) 紀錄放在 `tasks.yaml` 之外**(例如一份驗收紀錄檔),`tasks.yaml` 只引用
編號。好處是紀錄可以寫長;代價是多一層間接,而且要再寫一個檢查去驗那個引用
真的存在 —— 為了一年幾筆的紀錄,不值得。

**(c) 不做,接受 `manual` 就是口頭。** 誠實,但那等於承認 `done` 對 UI 類的
AC 沒有實質內容,而 CR-006 剛剛才拒絕過這個結論。

**建議 (a)。**

## 這條規則擋得住什麼、擋不住什麼

擋不住假簽:有人可以填一筆沒發生過的驗收。這跟 `check:cr` 驗裁決段是同一種
東西 —— 那條也擋不住造假,它防的是**忘了寫**。造假那層是 CODEOWNERS 要求的
人類 review,不是這裡。

我不建議把它做成更重的形式(例如要求附截圖路徑或簽章):成本落在每一次驗收,
而擋到的東西不會比「有沒有這筆紀錄」多。

## 波及範圍

- `contract/tasks.yaml`:欄位定義與 TASK-003 那兩條的補填(architect)
- `scripts/check-ac.mjs` 加一條規則、`scripts/check-ac.test.mjs` 加測試(infra,
  CR 一 accepted 就可以直接實作)
- 不動 `openapi.yaml`,不需要重新生成型別
- **上線當下不會紅**:TASK-003 是 `review`,規則只對 `done` 強制。等它要進
  `done` 的那一刻才會要求紀錄 —— 壓力落在對的地方,跟 CR-006 裁決「只對 done
  強制」的理由一致。

## 為什麼由 infra 提出

我在做 `pnpm dev:frontend`(#49)時撞到的:做完之後才發現「驗完之後把結果寫到
哪裡」沒有答案。工具備齊了,流程的最後一格是空的。
