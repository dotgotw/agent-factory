# CR-016: merge 通知的地址是 session_id —— 保證層應該從 git 推導

- **提出者**: architect
- **狀態**: proposed
- **阻擋任務**: 無

> 不阻擋任務,但它是 CR-015 的前提。CR-015 要求「一個任務一條 session,做完就關」,
> 而現行的 merge 通知是寄到 `session_id` 的 —— **關掉的那一刻,寄給它的通知就會
> 靜靜地掉在地上**。先修好地址,CR-015 才敢執行。

## 問題

現行機制(可運作,而且方向是對的):

```
infra 完成任務 → 送 PR → 人工 merge → 背景監聽偵測到 merged
                                    → 取得 session_id → postMessage 給相關 session
```

ADR-009:164 已經替這個機制背書過了:

> 靠 session 之間的訊息傳遞。快,但訊息不在 repo 裡……
> **訊息可以用來通知,不能用來保存。**

這條機制做的正是**通知**,不是保存 —— 用法合法。**壞的不是機制,是地址。**

`session_id` 指向一個**會消失的東西**。今天它還能用,是因為角色 session 幾乎不關;
CR-015 一旦落地(一個任務一條 session),地址失效就從例外變成常態:

| 情境 | 現在 | CR-015 之後 |
|---|---|---|
| 目標 session 還活著 | 收到 | 收到 |
| 目標 session 已關閉 | 罕見 | **常態,而且沒有人知道漏了** |

最後那格是重點:**沒有 error、沒有紅燈、沒有任何痕跡。** 一則掉在地上的通知跟
一則沒有發出的通知長得一模一樣。

## 影響

不改的話,兩條路二選一,而兩條都不好:

**一、不敢關 session,好讓地址一直有效。** 那就是把 CR-015 撤銷,回到 840k 的世界 ——
用每輪的稅金去買一個郵政信箱。

**二、關了,然後接受偶爾漏通知。** 漏掉的具體後果是:某個角色的 base 已經過期而它不知道,
繼續在舊的 contract / 舊的 scripts 上做事,直到送 PR 撞牆。這正是 merge watcher
當初要防的東西。

## 建議變更

**兩層,職責分開。不要把現有的東西換掉 —— 這是加一層,不是改一層。**

### 第一層:快路徑(維持現狀,一行都不用改)

背景監聽 → `postMessage` 到還活著的 `session_id`。低延遲,**盡力而為**。
它回答的問題是:「你剛才送的那張 PR merge 了。」

### 第二層:保證層(新增)—— 從 git 推導,不要建佇列

`pnpm role` 開場時,比對本 worktree 與 `origin/main`:

```bash
git rev-list --count HEAD..origin/main      # main 前進了幾個 commit
git diff --name-only HEAD...origin/main     # 那些 commit 碰了哪些檔案
```

把檔案清單拿去比對 `scope.json` 裡該角色的路徑,輸出一行:

```
main 領先 7 個 commit,其中 2 個碰到你的 scope(細節:pnpm role --incoming)
```

它回答的是**不同的問題**:「main 在你不在的時候動了,而且動到你依賴的東西。」

兩層答的不是同一題,所以不是重複:

| | 快路徑 | 保證層 |
|---|---|---|
| 問題 | 我那張 PR merge 了嗎 | main 有沒有在我腳下移動 |
| 延遲 | 即時 | 下次開場 |
| 可靠度 | 盡力而為 | **不可能漏** |
| 地址 | session_id(會消失) | worktree / 角色(持久) |

### 為什麼是推導,不是佇列

我原本想的是「寫進一個持久佇列,開場去拿」。**推導比它好,理由全在你們自己的 ADR 裡:**

1. **不必回答「它歸誰」。** ADR-009:158 說沒有擁有者的目錄是這個 repo 的反模式,
   ADR-002 就是為了修掉那種東西。一個 `notifications/` 佇列會立刻撞上同一個問題。
2. **不可能漂移。** 佇列會跟現實不一致(寫了沒消費、消費了沒刪、兩個 session 搶同一則);
   **git 就是唯一真相,推導出來的東西不可能跟它不一致。**
3. **這是同一招的第三次。** ADR-002:衍生物由重新生成把關。ADR-007:status 是算出來的,
   不是存的。這裡:通知是算出來的,不是寄存的。**這個 repo 已經有這個形狀了,
   不必發明新的。**

### 必須遵守的約束

ADR-009:105-113 規定 `pnpm role` 的開場輸出必須是**常數長度** —— 理由是那是
「每個 session 都要付、而且注意力最稀缺的那一刻」。

所以保證層**只印一行計數,不印內容**,細節用 `--incoming` 之類的指令查。
跟坑註解同一條規則,同一個理由。

### 一個我沒有答案的成本

`origin/main` 要新鮮才準,而這意味著 `pnpm role` 可能要碰網路 —— 那是在 SessionStart
hook 裡,會加延遲,而且離線會失敗。三個選項,我沒有把握哪個對:

- 用上次 fetch 到的 `origin/main`:零延遲,但可能是舊的(**會謊報「沒有東西」**)
- 開場 fetch,設短 timeout:準,但每個 session 開場都付一次網路延遲
- 不 fetch,只比對本地已知的 main:最保守,漏報但不誤報

**傾向第三個**,因為漏報會被下一次 fetch 補上,誤報則會訓練人忽略這行。但這是 infra
的地盤,請 infra 判斷 —— 我對 hook 的延遲預算沒有數字。

## 波及範圍

- **infra** —— `scripts/role.mjs`(新增比對與輸出)、`.claude/`(背景監聽維持原樣,
  不用動)。沒有型別重新生成,沒有 contract 變更,沒有編譯失敗。
- **architect(我)** —— 無。這份 CR 不需要改 `contract/`。
- **所有角色** —— 開場多一行輸出。若採用第三個選項(不 fetch),沒有任何延遲成本。

## 與 CR-015 的關係

**CR-016 是 CR-015 的前提,不是它的一部分。** 這也是為什麼另開一份:

- CR-015 講的是**什麼時候關 session**(任務邊界),受眾是每一個角色
- CR-016 講的是**關掉之後通知怎麼還能送到**,受眾是 infra 的兩支程式

把它們塞進同一份,讀 CR-015 的人會被 git 指令淹沒,而 infra 要實作時得從一堆行為
建議裡挑出那兩支程式。**受眾不同,家就不同** —— 這是 ADR-009 的第二問,套在 CR 上。

順序上,CR-016 應該先落地:CR-015 要求關 session,而關 session 在通知地址修好之前
是有損的。

## 為什麼是 CR 而不是傳訊息

`scripts/` 與 `.claude/` 都不是 architect 能寫的(ADR-003)。這是被擋下來的標準出口。

另外:這份 CR 的主題就是「寄到 session 的東西會掉」,用訊息發它會示範它自己在反對的事。

附帶一提,這份 CR 是 proposed,所以跟 CR-013 / CR-014 / CR-015 一樣,會讓
`pnpm verify` 紅在 `check-cr.test.mjs:127`。**那條 bug 必須先由 infra 修掉,
這四份 CR 才送得出 PR** —— 詳見 CR-014。
