# CR-005: 「每一條 AC 都有測試」沒有任何機制在驗

- **提出者**: qa
- **狀態**: proposed
- **阻擋任務**: 無

## 問題
`e2e/AGENTS.md` 的 Done 條件寫著「每一條 AC 至少有一個對應測試,且全數通過」,
但 `npm run verify` 只驗後半句。前半句 —— **覆蓋率** —— 沒有任何機制在看。

contract drift 有 `check:drift` 顧,CR 與 tasks.yaml 的一致性有 `check:cr` 顧,
唯獨「tasks.yaml 宣告了 AC-0NN,e2e 裡有沒有這一條」靠人記得。

實際跑一次交叉比對(臨時腳本,約十行):

```
任務         owner      status       AC 覆蓋
TASK-001   backend    done         AC-001✓ AC-002✓
TASK-002   backend    done         AC-003✓ AC-004✓
TASK-003   frontend   done         AC-005✗ AC-006✗
TASK-004   backend    blocked      AC-007✗
TASK-005   backend    todo         AC-008✗ AC-009✗
TASK-006   backend    done         AC-010✓ AC-011✓ AC-012✓
```

TASK-003 的狀態是 `done`,兩條 AC 都沒有測試。這個洞存在多久沒人知道 ——
它從來不會讓任何一次 `verify` 變紅。

## 影響
`check:cr` 的檔頭寫得很好:「CR 的狀態是 markdown 文字,沒有型別、沒有 schema,
靠人眼看不出漂移。本腳本補上這個缺口。」AC 覆蓋率是同一種漂移,只是還沒有人補。

差別在於後果的方向。少寫一條測試不會讓 CI 變紅,**它讓 CI 變得更綠** ——
沒有測試的 AC 不會失敗。所以這種漂移是單向的:只會越漏越多,不會自己修正。

而 qa 是唯一會發現它的角色,卻要靠「記得去比對」才發現。我這次是為了回答
「qa 怎麼知道自己要開工」才寫了那段臨時腳本,順手撞到的。

## 建議變更
`scripts/check-ac.mjs`,掛進 `npm run verify`。核心邏輯就是上面那張表:

```js
const acs = tasks.flatMap((t) => (t.acceptance ?? []).map((a) => [t, a]));
const covered = new Set(specsText.match(/AC-\d+/g) ?? []);
const missing = acs.filter(([t, a]) => t.status !== 'blocked' && !covered.has(a.id));
```

`status: blocked` 要排除 —— TASK-004 在等 CR-001 定義 `PATCH /projects/{id}`,
contract 都還沒有,寫了也沒有東西可測。

**但有一個政策問題要先決定:遇到「架構上測不到」的 AC 怎麼辦。**
見 CR-006 —— AC-005/AC-006 是 UI 驗收,現在的黑箱 e2e 打不到畫面。
若沒有豁免機制,這個檢查一掛上去就是永久紅燈,然後被人加 `|| true` 繞掉,
比不做還糟。可能的做法:tasks.yaml 的 AC 加一個 `verified_by` 欄位
(`e2e` | `manual` | `none`),檢查只管 `verified_by: e2e` 的那些。
不過那是 contract 的結構變更,得由 architect 裁決。

## 波及範圍
- 新增 `scripts/check-ac.mjs`、`package.json` 的 `verify` 加一段 —— 都是 infra 的路徑。
- 若採用 `verified_by` 欄位,`contract/tasks.yaml` 需要 architect 修改(見 CR-006)。
- 不動 `contract/openapi.yaml`,不需要重新生成型別。
- 掛上去的當下會立刻紅 —— 那是它在做事,不是它壞了。請先處理 CR-006 再合併本 CR。

## 為什麼由 qa 提出
`scripts/` 只有 infra 能寫。這個缺口是我在算 AC 覆蓋率時撞到的,
依 `AGENTS.md` 第 2 條開 CR,不自己動手。
