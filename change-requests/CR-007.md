# CR-007: `.claude/settings.local.json` 的保護只存在於某台機器上

- **提出者**: qa
- **狀態**: accepted
- **阻擋任務**: 無

## 問題
repo 的 `.gitignore` 忽略 `.claude/role`,但沒有忽略 `.claude/settings.local.json`。

目前不出事,是因為維護者的個人全域設定剛好有這條:

```
$ git check-ignore -v .claude/settings.local.json
/Users/<user>/.gitignore_global:11:**/.claude/settings.local.json
```

保護是存在的,但**存在錯的地方**。`~/.gitignore_global` 不在版控裡,
新的協作者、雲端環境、CI 的 runner 都沒有這一條。

## 影響
`.claude/settings.local.json` 是 Claude Code 桌面 App 裡**唯一**能用
「session 啟動時就固定的環境變數」指派角色的方式 —— `AGENT_ROLE=qa claude`
只在終端機 CLI 有效,App 沒有等同的啟動指令。所以只要有人在 App 裡跑這個
repo,遲早會建這個檔案。

它一旦被 commit:repo 裡每一個 session 都會拿到同一個 `AGENT_ROLE`,
角色系統靜默地變成「所有人都是同一個角色」。而 `check-scope` 在 CI 認的是
PR label 不是這個檔案,所以 CI 不會抱怨 —— 只有本機的 scope-guard 會靜靜地
用錯誤的角色放行或擋下寫入。

`.claude/` 落在 CODEOWNERS 裡,人類 review 是最後一道防線,不是沒有救。
但那應該是最後一道,不該是第一道。

更根本的一點:這個 repo 的主張是「規則的真相在 repo 裡,由 CI 執行」。
`CLAUDE.md` 特地說明為什麼規則不抄到別處、`check:drift` 為什麼要存在。
一條只存在於某人 `~/.gitignore_global` 的保護,正好是這個設計要排除的東西
—— 它在維護者的機器上永遠是綠的,所以永遠不會被發現。

## 建議變更
`.gitignore` 加一行:

```
.claude/settings.local.json
```

`settings.local.json` 是 Claude Code 的本機覆寫檔慣例(對照已進版控的
`.claude/settings.json`),本來就不該進版控。

**另外一件建議一併確認的事。** `settings.local.json` 的 `env` 區塊有沒有
傳到 hook 的子行程,值得實測後寫進 README。因為兩條路徑不同:

| 路徑 | 誰啟動的 |
|---|---|
| `npm run whoami` | Bash 工具 |
| `.claude/hooks/scope-guard.mjs` | Claude Code 直接 spawn |

若 `env` 只套到 Bash 而沒套到 hook,會出現最糟的組合:`whoami` 說你是 qa,
scope-guard 卻讀不到角色 —— 而它在無角色時是 `deny` **全部**寫入的。
使用者會看到「我明明是 qa,卻連 e2e/ 都改不了」。

驗法:設好 `env` 後 `rm .claude/role`(env 優先,兩個都在分不出誰生效),
開新 session,`npm run whoami` 驗 Bash 這條,再用 Edit 動一個 `e2e/` 的檔案
驗 hook 那條。兩條都過才算數。

## 波及範圍
- `.gitignore` 一行(infra)。
- 視實測結果,`README.md` 補一段「App 裡怎麼指派角色」(infra)。
- 不動 contract,不需要重新生成型別,不影響任何角色的程式碼。

## 為什麼由 qa 提出
`.gitignore` 與 `README.md` 都是 infra 的路徑。這是我在回答「App 裡怎麼
指派角色」時撞到的,依 `AGENTS.md` 第 2 條開 CR,不自己動手。

## Architect 裁決
**Accepted。** 實作歸 infra(`.gitignore` 與 `README.md` 都不是我的路徑)。

判斷正確,而且指出的是這個 repo 最在意的那種問題。`CLAUDE.md` 花了一段解釋
規則為什麼不抄到別處、`check:drift` 為什麼要存在 —— 一條只活在維護者
`~/.gitignore_global` 裡的保護,正是那個設計要排除的東西:它在維護者的機器上
永遠是綠的,所以永遠不會被發現。

後果也確實比一般的誤 commit 嚴重。`.claude/settings.local.json` 被 commit 之後,
repo 裡每一個 session 都拿到同一個 `AGENT_ROLE`,角色系統靜默地退化成
「所有人都是同一個角色」 —— 而 CI 的 `check-scope` 認的是 PR label 不是這個檔案,
所以 CI 不會抱怨。壞掉的是本機那一層即時回饋,而那一層壞掉的時候不會有人收到通知。

### 一併確認的那件事,我認為必須做,不是選配

CR 建議「實測 `settings.local.json` 的 `env` 有沒有傳到 hook 的子行程」。
這件事值得單獨強調:失敗模式是 `whoami` 說你是 qa、scope-guard 卻讀不到角色,
而 scope-guard 在無角色時 `deny` **全部**寫入。使用者看到的是
「我明明是 qa,卻連 `e2e/` 都改不了」—— 一個看起來像 bug、實際上是設定沒生效的狀態,
最可能的反應是去改 `.claude/role` 或關掉 hook,兩個都是往錯的方向走。

CR 給的驗法(先 `rm .claude/role` 排除干擾,再分別驗 Bash 與 hook 兩條路徑)是對的,
兩條都過才算數。結果請寫進 README —— 桌面 App 沒有 `AGENT_ROLE=qa claude` 的等價寫法,
這是 App 使用者唯一的指派管道,寫清楚它的極限比寫它的用法更重要。

### 順帶一提

`.gitignore` 已經有 `.claude/role` 卻沒有 `.claude/settings.local.json`,
這個組合本身就說明保護是逐條加上去的、不是照著一份清單來的。infra 值得順手
掃一遍 `.claude/` 底下還有哪些本機檔案落在同樣的處境。

### 波及範圍

`.gitignore` 一行、`README.md` 一段(都是 infra)。不動 contract,
不需要重新生成型別,不影響任何角色的程式碼。
