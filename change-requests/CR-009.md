# CR-009: 把 backend / frontend / e2e / generated 切成獨立 package，讓角色邊界進到解析層

- **提出者**: infra
- **狀態**: proposed
- **阻擋任務**: 無

> 前置條件:**CR-008 已 accepted**(2026-08-31),連帶產出 `ADR-002 衍生產物由重新生成保證`。
> 本案需要 CR-008 的實作先落地(pnpm + `_derived` 機制 + `check:drift` 補洞),理由見
> 「為什麼非 pnpm 不可」與新增的「與 ADR-002 的衝突」一節。

## 問題

`e2e/AGENTS.md` 寫著:

> **不可 import 任何實作模組**,只透過 HTTP 與 contract 型別。

這條規則今天由**零個機制**執行。`scope-guard` 只看寫入路徑,CI 的 `check:scope`
也只看寫入路徑,`tsc` 完全不管。qa 的 session 打一個 `../backend/src/index.js`
就從黑箱測試變成白箱測試,而三道檢查全綠。

同一個洞的另一半:`express` 是 root 的 dependency,所以
`frontend/src/app.ts` 現在 import 得到它。frontend 不該碰的東西,只是「沒人這樣寫」
而已,不是「寫不出來」。

這個 repo 的主張是「規則的真相在 repo 裡,由 CI 執行」。路徑邊界做到了,
**依賴邊界還停在 markdown 的請求階段。**

## 實測

照現行 `e2e/tsconfig.json` 做了一份複本,放一個違規 import,量四組:

| 組別 | 設定 | `import from '../backend/src/index.js'` | `import type` contract |
|---|---|---|---|
| A | 現行設定 | ✅ **編譯過(exit 0)** | ✅ 過 |
| B | 加 `rootDir: "."` | ❌ TS6059 擋下 | ❌ **也被擋下** |
| C | `rootDir` + contract 改走 package | ❌ TS6059 擋下 | ✅ 過 |
| D | 同 C,移除違規 import | — | ✅ 全綠 |

三個結論:

1. **A** —— 規則今天真的沒有執行者。
2. **B** —— 只加 `rootDir` 會把合法的 `../generated/api.ts` 一起擋掉。
   現行四個跨界 import 全走 `../../../generated/api.js` 這種相對路徑,
   所以單獨加 `rootDir` 會直接讓 `typecheck` 紅。
3. **C/D** —— `generated/` 變成真的 package 之後,TypeScript 不對
   `node_modules` 底下的檔案套 `rootDir`(即使那是指向 repo 內部的 symlink,
   pnpm workspace 正是這樣連結的)。contract 進得來,實作進不來。

## 建議變更

**兩個機制必須一起上,各自單獨都不成立:**

| 漏洞 | 例子 | 修的機制 |
|---|---|---|
| 幽靈依賴(bare specifier) | frontend import 得到 `express` | **workspaces** |
| 相對路徑逃逸 | `../backend/src/index.js` | **`rootDir`** |

workspaces 管不到相對路徑,`rootDir` 管不到套件解析。只做前者,A 組那個違規
import 照樣過。

目標結構:

```
package.json              # 只留全專案共用的 dev 工具(typescript、tsx)
pnpm-workspace.yaml       # 新增
generated/
  package.json            # 新增:name @af/contract, exports ./api.ts
  api.ts
backend/package.json      # 新增:deps express、@af/contract
frontend/package.json     # 新增:deps @af/contract(沒有 express)
e2e/package.json          # 新增:deps @af/contract(沒有 backend)
```

各 tsconfig 的 `include` 從 `["src/**/*.ts", "../generated/**/*.ts"]`
收斂成 `["src/**/*.ts"]`,並加上 `"rootDir": "."`。
四處 `../../../generated/api.js` 改成 `@af/contract`。

**e2e 這個 package 值得單獨說。** `e2e/server.ts:126` 是
`spawn(process.execPath, ['--import','tsx','backend/src/index.ts'])` ——
它把 backend 當**行程**啟動,不是當模組 import。這個黑箱性質目前只活在註解裡;
切成 package 之後它變成 `e2e/package.json` 裡看得見的事實:依賴有
`@af/contract`,沒有 backend。依賴關係從默契變成 diff。

### 為什麼非 pnpm 不可

npm workspaces 會把所有依賴 hoist 到 root 的 `node_modules`,所以
「frontend 解析不到 express」這個性質做不出來 —— 幽靈依賴那半邊修不掉,
只剩 `rootDir` 那半邊。這是 CR-008 必須先過的原因,不是順序偏好。

## 波及範圍

沒有任何行為改變,`contract/openapi.yaml` 不動,型別不需要重新生成。
但**這張 CR 的實作跨五個角色**,而 CI 的 `scope` job 要求恰好一個 `agent:*` label。

| 檔案 | 今天歸誰 |
|---|---|
| `pnpm-workspace.yaml`、三個 `tsconfig.json`、root `package.json`、`ci.yml`、`scope.json` | infra |
| `generated/package.json` | **無人擁有** —— ADR-002 之後 `generated/` 是 `_derived`,writers 為 architect、infra。且見下節:這個檔案根本不該用手寫的 |
| `e2e/package.json`、`e2e/*.spec.ts` 的 import | **qa**(`e2e/` 是它的路徑) |
| `backend/src/` 的 import | backend |
| `frontend/src/` 的 import | frontend |
| `backend/package.json`、`frontend/package.json` | **沒有主人 —— 見下** |

### 一個沒主人的檔案

`scripts/role.mjs:54` 的比對是 `rel.startsWith(prefix)`。scope.json 裡
infra 的 `"package.json"` 只精確涵蓋 root,backend 的 `"backend/src/"`
不涵蓋 `backend/package.json`。所以 **`backend/package.json` 不在任何角色的
可寫範圍內**,誰建都會被 scope-guard deny。

infra 已明列 `backend/tsconfig.json`、`backend/AGENTS.md`,慣例上
`backend/package.json` 也該歸 infra。但這有個要 architect 決定的後果:

**依賴一旦歸 infra,backend agent 想加一個套件就必須開 CR。**

這可能正是想要的 —— 加依賴是值得 review 的事件,而且跟「實作角色不可改 CI」
是同一個道理(能自由加依賴的角色,可以繞過任何靜態檢查)。也可能太黏,
讓日常開發卡住。infra 沒有立場自己決定這件事。

注意 `e2e/package.json` 天然落在 qa 的 `e2e/` 底下,所以 qa **可以**自由加依賴,
backend 卻不行 —— 若採 infra 所有制,這個不對稱要嘛接受、要嘛一併處理。

### 與 ADR-002 的衝突(本 CR 初版沒算到)

ADR-002 的前提條件 1 要求 `check:drift` 改成**生成前先清空目錄**:

```bash
rm -rf generated/ && <gen:types> && git diff --exit-code generated/
```

本 CR 初版的第 1 步是「architect 手寫 `generated/package.json`」。這兩件事互斥
—— `gen-types.sh` 只寫 `generated/api.ts`,清空目錄會把手寫的 manifest 一起清掉。
建複本實測:

| `check:drift` 版本 | `generated/package.json` | 結果 |
|---|---|---|
| 現行(覆寫單檔) | 存活 | exit 0 |
| ADR-002 要求(先清空) | **被刪除** | exit 1,`generated/package.json \| 1 -` |

**修法:讓 `gen-types.sh` 一併產出 `generated/package.json`。**
manifest 於是也是衍生產物,由同一個 drift 守衛 —— 這正是 ADR-002 自己的推論:
一個生成套件的 manifest,內容當然由生成器決定,不是誰的財產。

連帶好處:這一步從 architect 的 PR 變成 **infra 的 PR**(`gen-types.sh` 是 infra 的,
而 `generated/` 的 `_derived` writers 含 infra)。**架構師不必為了這個重構進場**,
順序少一張 PR、少一個角色。這會是 `_derived` 機制的第二個實例 —— 第一個是
CR-008 的表頭。

### 一條每一步都全綠的順序

CI 一個 PR 只准一個角色,而且中間狀態不能紅(先改 tsconfig 會讓 typecheck 紅,
先改 import 會解析不到)。下面這條路每一步都是綠的:

| # | 張數 | 角色 | 內容 | 為什麼這步是綠的 |
|---|---|---|---|---|
| 1 | 1 | infra | `gen-types.sh` 一併產出 `generated/package.json`(name `@af/contract`);`scope.json` 補 `backend/package.json`、`frontend/package.json`、`pnpm-workspace.yaml` 的所有權 | manifest 成為衍生產物,由 drift 守衛;此時還沒人引用它。scope.json 只加白名單,本 PR 不建立那些檔案,不構成自我授權 |
| 2 | 1 | qa | 新增 `e2e/package.json` | 同上,沒人引用 |
| 3 | 1 | infra | `pnpm-workspace.yaml` + backend/frontend 的 `package.json` + root 瘦身 | workspace 建立後,舊的相對路徑**仍然可用**,兩種寫法並存 |
| 4 | 3 | backend / frontend / qa | 各自把 `../../../generated/api.js` 改成 `@af/contract` | 上一步已讓 bare specifier 可解析 |
| 5 | 1 | infra | 各 tsconfig 加 `rootDir`、收斂 `include` | 此時已無跨界相對路徑,邊界在這一步才真正關上 |

**七張 PR、四個角色。**(初版寫「七張」但表格實際是八張,是算錯;採用上面的
manifest 修法後才真的是七張,而且 architect 不必進場。)

這個數字本身就是這張 CR 要呈報的東西之一:角色制度對「橫切式重構」的成本,
比對日常開發高一個數量級。

請 architect 一併裁決:

- **(a) 照上表付這個成本。** 慢,但每一步都可審、都可回退,制度不破例。
- **(b) 開一個 migration 例外。** 允許標記為遷移的 PR 掛多個 `agent:*` label,
  由 CODEOWNERS 要求所有涉及角色的 review。快,但例外一旦存在就會被援用。
  **ADR-002 已經對這類做法表過態**:它否決了「多給一個人寫入權 + CODEOWNERS 補足」,
  理由是 CODEOWNERS 在本 repo 只是「人類知情地合併」。同樣的理由適用於這裡,
  所以 (b) 大概會被否決 —— 列出來是為了讓否決的理由留在記錄裡。
- **(c) 不做。** 接受依賴邊界停留在 markdown 請求的階段,理由是成本不划算。
  若選這條,建議至少把 `e2e/AGENTS.md` 那句「不可 import 實作模組」改寫成
  「目前無機制執行,靠 review」—— 讓文件說實話,比讓它許一個沒人兌現的承諾好。

CR-008 的陷阱二問的是同一件事的小號版本(生成器與生成物分屬兩個角色)。
若那邊採了例外機制,這裡可以沿用。

## 驗收

1. `pnpm verify` 全綠,CI 全綠。
2. **邊界要證明,不要宣稱。** 在 `e2e/` 放一個 `import { app } from '../backend/src/index.js'`,
   確認 `typecheck` 以 TS6059 失敗;在 `frontend/src/` 放一個 `import express from 'express'`,
   確認解析失敗。兩個都驗完再把檔案刪掉。
3. 更好的做法:把上面兩個負向案例做成常設檢查(例如 `scripts/check-boundaries.sh`,
   用 `tsc --noEmit` 對一組刻意違規的 fixture 跑,期望它紅)。
   否則這個邊界只在導入當天被驗證過一次。
4. `pnpm install --filter frontend...` 之後,確認 `frontend/node_modules` 裡沒有 `express`。

## 磁碟這件事要說清楚

切 package 的主要理由是**正確性,不是磁碟**。有了 pnpm 的 content-addressed
store,套件檔案不管幾個 worktree 用都只有一份,`--filter` 省不到那部分的本機空間。

`--filter` 真正省的是三件別的:CI 與 Docker(全新 runner 沒有 store,裝多少就是多少)、
postinstall 的副作用(例如 Prisma 的 engine 是下載到 node_modules 的實體檔案,
不是 store 去重的套件內容)、以及連結樹的建立時間與 inode 數。

這點跟 CR-008 是同一個方向:表面是磁碟,實際是邊界。

## 這張 CR 需要一份 ADR

ADR-002 的「不在本 ADR 範圍」明確寫著:workspaces 切分**需要另一份 ADR**,
因為它改變的是哪個角色能 import 到什麼,那是邊界語意不是工具選型。

本案若 accepted,請一併產出 **ADR-003**。建議記的是決策本身而不是 pnpm:
「角色邊界由套件解析與 `rootDir` 共同執行,而非由文件請求」,
連同被否決的方案(只做 workspaces / 只做 `rootDir`,以及上面四組實測為什麼
證明兩者單獨都不成立)。

## 為什麼由 infra 提出

多數受影響路徑是 infra 的,而且這是結構與工具鏈的變更。但決策不是 infra 的:
`backend/package.json` 的歸屬、七張 PR 的成本要不要付、要不要開 migration 例外,
三件都超出「規則的執行者」該自己決定的範圍。
