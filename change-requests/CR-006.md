# CR-006: AC-005/AC-006 是 UI 驗收,黑箱 e2e 架構上測不到

- **提出者**: qa
- **狀態**: accepted
- **阻擋任務**: 無

## 問題
TASK-003(frontend,`status: done`)的兩條驗收條件:

| AC | 內容 |
|---|---|
| AC-005 | 顯示名稱、狀態、建立日期 |
| AC-006 | 無資料時顯示空狀態 |

兩條都沒有測試,而且**不是誰忘了寫** —— 現在的 `e2e/` 只會 spawn backend
再對它發 HTTP 請求,打不到畫面。`package.json` 裡也沒有任何把 frontend
跑起來的指令(只有 `dev:backend`),所以連「把它服務起來再測」的前置條件
都不存在。

換句話說:TASK-003 標成 `done`,但它的驗收條件從來沒有被驗收過。

## 影響
這不只是少兩個測試,它讓 `status: done` 這個欄位的意思變得不一致 ——
backend 的 done 表示「AC 有測試而且綠」,frontend 的 done 表示「有人覺得做完了」。
同一個欄位兩種標準,而讀 tasks.yaml 的人(以及 `check:cr` 這類腳本)分不出來。

往前看還會更糟:TASK-003 之後每一個 frontend 任務都會複製這個狀態。
現在只有兩條 AC 懸空,晚一點就是十條。

CR-005 提議加「AC 覆蓋率」檢查,但那個檢查一掛上去,AC-005/AC-006 就是永久紅燈。
所以這兩張 CR 綁在一起:**先決定這類 AC 怎麼驗收,覆蓋率檢查才有辦法上線。**

## 建議變更
不是 openapi.yaml 的變更,是驗收方式的決策。三條路,由 architect 選:

1. **加一層瀏覽器測試。** e2e 多一個 spec 檔,把 frontend 服務起來後用
   真的瀏覽器驗。最完整,但引入新的依賴與 CI 時間,而且需要 infra 先提供
   「把 frontend 跑起來」的指令。
2. **承認這類 AC 不歸黑箱 e2e 管。** 在 tasks.yaml 的 AC 上標記驗收方式
   (例如 CR-005 提到的 `verified_by: e2e | manual | none`),UI 類的走人工
   驗收。誠實,成本低,但「done」的實質保障確實變弱了 —— 至少它變成**寫出來的**弱,
   而不是現在這種沒人講的弱。
3. **把 AC 改寫成打得到的形式。** 例如 AC-005 改成驗「列表 API 回傳的欄位
   足以渲染名稱、狀態、建立日期」。但這是把驗收條件遷就測試能力,
   AC-006(空狀態)這種純畫面的條件也救不回來。我不建議。

我傾向 2,並且把 TASK-003 的 `done` 維持原狀但補上 `verified_by`,
讓「沒有自動化測試」這件事變成 tasks.yaml 裡看得見的事實。

## 波及範圍
- 選 1:需要 infra 提供 frontend 的啟動指令,`e2e/` 新增 spec(qa),CI 時間增加。
- 選 2:`contract/tasks.yaml` 的 AC 結構變更(architect),`scripts/check-ac.mjs`
  需配合(infra,見 CR-005)。不動 openapi.yaml,不需要重新生成型別。
- 選 3:改寫 AC 文字(architect),qa 補測試。
- 三條路都不影響 backend 與 frontend 的現有程式碼。

`contract/` 只有 architect 能寫。我在算 AC 覆蓋率時發現這兩條懸空,
但「這類 AC 該怎麼驗收」不是 qa 能決定的 —— 我只能說現在的架構測不到。

## Architect 裁決
**Accepted，採選項 2,但對提案的 enum 做了兩處修改。**

`contract/tasks.yaml` 的每一條 acceptance 現在都必須宣告 `verified_by`。

### 為什麼不是選項 1 或 3

選項 1(瀏覽器測試)要先讓 infra 提供「把 frontend 跑起來」的指令,再讓 qa
寫 spec,再讓 CI 吞下多出來的時間 —— 那是另一條供應鏈,不該擋在「先把現況
講清楚」前面。它是好的下一步,不是這一步:等 `verified_by` 就位,把 AC-005/006
從 `manual` 改成 `e2e` 就是一行變更,而且改的當下 `check:ac` 立刻開始要求測試。

選項 3 是把驗收條件遷就工具能力。qa 自己不建議,我同意 —— AC-006(空狀態)
改寫成 API 層的斷言之後,驗的已經不是原本那條 AC 了。

### 修改一:沒有 `none`

提案的 enum 是 `e2e | manual | none`。我拿掉 `none`。

CR-005 自己講得很準:少寫一條測試不會讓 CI 變紅,**它讓 CI 變得更綠**,
所以這種漂移是單向的。`none` 是一個零成本的逃生門 —— 任何一條難測的 AC
都可以標成 `none` 讓檢查閉嘴,而且標了之後沒有任何機制會再提起它。
給單向漂移一個零成本出口,等於把它制度化。

`manual` 另外要求 `verified_note` 寫明為什麼自動化測不到。這不是形式:
它逼提出的人講出理由,而理由是可以在 review 被反駁的。「打不到畫面」成立,
「還沒空寫」不成立 —— 後者的正解是任務留在 `review`,不是改 `verified_by`。

### 修改二:TASK-003 從 `done` 改成 `review`

qa 建議「維持 done 但補上 `verified_by`」。我不同意,而且理由正是這張 CR 的主旨。

`verified_by: manual` 的意思是「由人工驗收」,不是「不必驗收」。而 AC-005/006
的人工驗收**從來沒有發生過** —— 沒有紀錄、沒有人聲稱做過。維持 `done` 的話,
這張 CR 指出的問題(「frontend 的 done 表示有人覺得做完了」)原封不動,
只是多了一個欄位在旁邊看著。

`review` 是狀態機裡本來就有的值,語意剛好:實作完成,等待驗收。這樣
`done` 對兩個角色重新變成同一個意思 —— **所有 AC 都依其 `verified_by` 完成驗收**。
TASK-003 要進 done,需要有人真的看過那兩條並留下紀錄。

這不是把 frontend 的工作退回去。程式碼在、功能在,退回去的是「已驗收」這個宣稱。

### `check:ac` 的規格(交給 CR-005 / infra 實作)

裁決連帶定義這個檢查該長什麼樣,免得 infra 得回頭猜:

| 規則 | 內容 |
|---|---|
| 觸發時機 | 只對 `status: done` 的任務強制 AC 覆蓋率 |
| `verified_by: e2e` | `e2e/` 裡必須找得到該 AC 編號,否則紅 |
| `verified_by: manual` | 跳過覆蓋率,但必須有非空的 `verified_note`,否則紅 |
| 欄位缺漏 | 任何 AC 沒有 `verified_by` 就紅(不給預設值) |

**「只對 done 強制」比 CR-005 提案的「排除 blocked」更準。** 提案的規則會讓
AC-008/009(TASK-005,`todo`)當場紅 —— 那個任務還沒開工,沒有測試是正常的,
不是漂移。改成在 `done` 這一刻強制,壓力就落在對的地方:**要標 done,先讓
AC 有測試。** 這也順帶讓 `review` 成為一個有用的中繼狀態而不是裝飾。

### AC-008 刻意標成 `e2e`

TASK-005 的通知功能還沒實作,而「寄出通知」是 API 表面之外的副作用,
現在無法斷言它到底測不測得到。標成 `e2e` 是刻意的:它要求 backend 把實作
做成可觀測的形式,而不是先寫死成不可測、再回頭申請 `manual`。

若實作後確認黑箱真的驗不到,那時再開 CR 改成 `manual` —— 帶著具體的實作
細節來談,比現在憑空猜測有意義。

### 波及範圍(實測)

`npm run verify` 全綠。`verified_by` 是 tasks.yaml 的新欄位,`check:cr` 只讀
`status` 與 `blocked_reason`,不受影響;不動 `openapi.yaml`,不需要重新生成型別。
TASK-003 由 done 改為 review 不影響任何腳本(`check:cr` 只特別處理 `blocked`)。
