# CR-003: GET /projects 缺少分頁機制

- **提出者**: backend
- **狀態**: accepted
- **阻擋任務**: TASK-005

## 問題
實作 TASK-005 的通知邏輯時,需要掃過所有專案找出有 `ownerEmail` 的對象。
但 `GET /projects` 定義的回應是一次回傳完整陣列,沒有 `limit` / `offset`,
回應中也沒有總筆數。專案數量成長後,這個端點會變成效能瓶頸。

## 影響
不改 contract 的話,只剩兩條路:
1. 自己在 openapi.yaml 加參數 —— 違反邊界規則,`scope` 會擋(見 PR #1)。
2. 在 backend 私自支援未寫入 contract 的 query string —— frontend 拿不到型別,
   QA 也測不到,等於隱藏功能。

兩條都不該走,所以停下任務、開這份 CR。

## 建議變更
在 `paths./projects.get.parameters` 新增兩個選填參數:

```yaml
- name: limit
  in: query
  required: false
  schema:
    type: integer
    minimum: 1
    maximum: 100
    default: 20
- name: offset
  in: query
  required: false
  schema:
    type: integer
    minimum: 0
    default: 0
```

並在 200 回應的物件中新增必填欄位 `total`(integer),用於前端計算頁數。

## 波及範圍
- `generated/api.ts`:query 參數為選填,屬非破壞性;
  但 `total` 加入 `required` 會是**破壞性變更**,既有讀取回應的程式碼需調整。
- frontend:TASK-003 的列表畫面需處理分頁,型別會編譯失敗直到補上。
- QA:AC-003 需擴充,另需新增分頁邊界的驗收條件。
- 因含破壞性變更,建議 `info.version` 升至 `1.1.0`。

---
## Architect 裁決
**Accepted,但分三階段實施。**

### 提案中的波及範圍評估有誤

實測結果與提案所述相反:

| | 提案宣稱 | 實測 |
|---|---|---|
| backend | 未提及 | ❌ `res.json({ items })` 缺 `total`,編譯失敗 |
| frontend | 會編譯失敗 | ✅ 通過(`const { items } = ...` 只解構 items) |
| e2e | 未提及 | ✅ 通過 |

`total` 加入 `required` 影響的是**產生**回應的一方(backend),
而非**消費**的一方(frontend)。回應多出欄位對消費者是相容的。

### 為何不能一次做完

若本次直接將 `total` 設為必填:

1. architect 的 PR 會讓 `backend/src/routes/projects.ts` 編譯失敗
2. architect **無權修改** `backend/src/`(allow 僅 `contract/`、`generated/`)
3. backend 需要新型別才能補上 `total`,但新型別在這個進不去的 PR 裡

死結。這不是流程缺陷,而是破壞性變更的本質:
**契約與實作無法在同一個原子操作中同時改變。**

### 三階段(expand / contract)

| 階段 | 角色 | 內容 | contract 相容性 | 完成 |
|---|---|---|---|---|
| 一 | architect | 新增 `limit`/`offset`;`total` **選填**;升版 1.1.0 | 非破壞性 | #7 |
| 二 | backend | 實作分頁,回應帶上 `total` | — | #9 |
| 二之補 | qa | AC-010~012 的 e2e 驗收測試 | — | #11 |
| 三 | architect | `total` 改為 **必填**;升版 2.0.0 | 破壞性 | 本 PR |

每個階段各自都是綠燈,合起來達成提案的完整目標。

### 版本

`info.version` 於階段一升至 `1.1.0`(新增端點參數,非破壞性),
階段三升至 `2.0.0`(`total` 加入 `required`,破壞性)。

### 階段三結案紀錄

`total` 改為必填後 typecheck **直接通過**,無須任何實作調整 ——
因為階段二已先讓 backend 回傳該欄位。這正是 expand/contract 的目的:
把「契約與實作必須同時改變」的原子性需求,拆成兩次各自安全的變更。

qa 於階段二之補(#11)已用突變測試驗證分頁行為有測試保護,
故本階段的收緊動作是在守衛就位的前提下進行。
