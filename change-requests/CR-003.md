# CR-003: GET /projects 缺少分頁機制

- **提出者**: backend
- **狀態**: proposed
- **阻擋任務**: TASK-005

## 問題
實作 TASK-005 的通知邏輯時,需要掃過所有專案找出有 `ownerEmail` 的對象。
但 `GET /projects` 定義的回應是一次回傳完整陣列,沒有 `limit` / `offset`,
回應中也沒有總筆數。專案數量成長後,這個端點會變成效能瓶頸。

## 影響
不改 contract 的話,只剩兩條路:
1. 自己在 openapi.yaml 加參數 —— 違反邊界規則,`scope` 會擋(見 PR #1)。
2. 在 backend 私自支援未寫入 contract 的 query string —— frontend 拿不到型別,
   QA 也測不到,等於隱藏功能。

兩條都不該走,所以停下任務、開這份 CR。

## 建議變更
在 `paths./projects.get.parameters` 新增兩個選填參數:

```yaml
- name: limit
  in: query
  required: false
  schema:
    type: integer
    minimum: 1
    maximum: 100
    default: 20
- name: offset
  in: query
  required: false
  schema:
    type: integer
    minimum: 0
    default: 0
```

並在 200 回應的物件中新增必填欄位 `total`(integer),用於前端計算頁數。

## 波及範圍
- `generated/api.ts`:query 參數為選填,屬非破壞性;
  但 `total` 加入 `required` 會是**破壞性變更**,既有讀取回應的程式碼需調整。
- frontend:TASK-003 的列表畫面需處理分頁,型別會編譯失敗直到補上。
- QA:AC-003 需擴充,另需新增分頁邊界的驗收條件。
- 因含破壞性變更,建議 `info.version` 升至 `1.1.0`。
