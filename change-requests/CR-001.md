# CR-001: 缺少專案封存端點

- **提出者**: backend
- **狀態**: accepted
- **阻擋任務**: TASK-004

## 問題
`tasks.yaml` 的 TASK-004 要求封存功能,但 `openapi.yaml` 沒有任何可以修改
`Project.status` 的端點。Project schema 有 `archived` 這個 enum 值,卻沒有
路徑能把專案切換過去。

## 影響
不改 contract 的話,我只有兩條路:
1. 自己在 openapi.yaml 加一個端點 —— 違反邊界規則。
2. 硬做一個沒寫進 contract 的隱藏端點 —— frontend 拿不到型別,QA 測不到。

兩條都不該走,所以停下這個任務、開這份 CR。

## 建議變更
新增 `PATCH /projects/{projectId}`,request body:

```yaml
UpdateProjectRequest:
  type: object
  properties:
    status:
      $ref: '#/components/schemas/ProjectStatus'
```

## 波及範圍
- `generated/api.ts` 新增 operation,屬純新增,不會破壞既有程式碼。
- frontend 需新增一顆封存按鈕(TASK-005,待建)。
- QA 需為 AC-007 補測試。

---
## Architect 裁決
**Accepted。** 已在 `contract/openapi.yaml` 新增 `PATCH /projects/{projectId}`
與 `UpdateProjectRequest` schema,`info.version` 由 2.0.0 升至 **2.1.0**。
`tasks.yaml` 的 TASK-004 由 `blocked` 改為 `todo`。

### 與提案的兩點差異

**1. `status` 設為必填,不是選填。**

提案的 schema 沒有 `required`。但這個 body 目前只有一個欄位,選填的話 `{}`
是一次合法的請求 —— backend 回 200、什麼都沒改,呼叫端看不出哪裡不對。
設為必填,這種請求變成 400 `VALIDATION_ERROR`,落回既有的 Error 慣例。

方向也是安全的那一邊。CR-003 學到的是「放寬容易、收緊難」:

| 動作 | 對既有 client |
|---|---|
| 從 required 移出 status(日後新增可更新欄位時) | 相容 |
| 把 status 加進 required(現在不做、日後才做) | 破壞性,要升 major |

所以現在嚴、日後鬆,是可逆的那個選擇。

**2. 只放 `status`,不放 `name` 與 `ownerEmail`。**

CR-001 要解決的是 TASK-004 的封存功能,AC-007 也只談狀態。把 `name` /
`ownerEmail` 一起開放是順手擴大 contract,而那些欄位沒有任何 AC 在驗
—— 要改請另開 CR,連同驗收條件一起提。

`status` 用的是 `ProjectStatus` enum,所以 `archived → active`(取消封存)
同樣合法。AC-007 沒有要求這件事,但刻意不擋 —— 單向的狀態機要另外寫進
contract 才算數,不該靠「沒實作」來達成。

### 版本

2.0.0 → **2.1.0**。新增一個 operation 是純增量:既有的 `listProjects`、
`createProject`、`getProject` 型別完全沒動,`generated/api.ts` 的 diff 全是新增。
backend 尚未實作這個端點不會讓任何東西編譯失敗。

### 波及範圍(實測)
