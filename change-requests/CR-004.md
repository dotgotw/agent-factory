# CR-004: e2e 會誤連到殘留的 server,重跑就紅

- **提出者**: infra
- **狀態**: proposed
- **阻擋任務**: 無

## 問題
`e2e/*.spec.ts` 用固定 port 啟動 backend(pagination 3998、projects 3999),
但 `waitForServer()` 只確認「port 上有東西回應」,沒有確認那個東西是**這次
spawn 出來的行程**。

前一輪測試若沒把 server 收乾淨(中斷、逾時、CI 外的本機重跑),殘留行程仍
佔著 port。下一輪 `spawn` 綁不到 port 會立刻失敗,但 `stdio: 'ignore'` 把
錯誤吞掉,`waitForServer()` 接著連上**舊的** server —— 測試於是對著一個
帶著上一輪 25 筆資料的 server 做斷言。

實測(2026-08-29,本機):第一次跑 14/14 綠,之後每一次都是同樣 4 項紅,
全部集中在分頁的筆數斷言:

```
not ok 4 - AC-010: offset 超出總數時回空陣列而非報錯
not ok 5 - AC-011: total 為分頁前的總筆數,不隨 limit 改變
not ok 6 - AC-011: total 反映 status 篩選的結果
not ok 10 - 邊界: limit=1 與 limit=100 皆為合法
```

手動 `kill` 掉殘留行程後,連跑兩次 `npm run verify` 都是綠的。在 `main`
上跑三次同樣三次紅,確認與任何 PR 無關。

## 影響
CI 每次都是全新 runner,所以**這個問題在 CI 永遠看不到**——只有本機重跑
會遇到。後果是最糟的那一種:

1. 開發者本機看到紅燈,但 diff 明明沒碰 backend,於是把它當成 flake 忽略。
   下次真的有回歸時,同一批斷言再紅一次,一樣被當 flake。
2. 更糟的方向 —— 為了讓本機變綠而去放寬那 4 項斷言。`AGENTS.md` 第 3 條
   禁止實作角色改 `e2e/`,但這條規則擋不住「因為誤判而做出的合理修改」。

測試對著一個來路不明的 server 做斷言,結果無論綠紅都沒有意義。這比測試
失敗更嚴重。

## 建議變更
不是 contract 變更,是 `e2e/` 的健壯性修正。兩個檔案的 `before()` 都適用:

1. **啟動前先確認 port 是空的。** 已經有人在聽就直接 `throw`,明確告訴
   開發者「有殘留行程」,而不是安靜地測錯對象。

   ```ts
   async function assertPortFree(): Promise<void> {
     try {
       await fetch(`${BASE}/projects`, { signal: AbortSignal.timeout(500) });
     } catch {
       return; // 連不上 = port 是空的,正常路徑
     }
     throw new Error(`${BASE} 已經有 server 在聽 —— 請先關掉殘留行程再跑測試`);
   }
   ```

2. **`spawn` 的錯誤不要吞掉。** `stdio: 'ignore'` 讓 EADDRINUSE 完全消失。
   至少把 stderr 導出來,或監聽 `server.on('exit')`,行程提早死掉就讓
   `before()` 失敗。

3. **`after()` 確保收乾淨。** 確認目前的 teardown 在測試中途 throw 時仍會
   執行,必要時改用 `SIGKILL` 並 await 行程真的結束。

改用隨機 port 也能解,但會失去「固定 port 好 debug」的好處,而且沒有解決
「spawn 失敗被吞掉」這個更根本的問題。建議先做 1 和 2。

## 波及範圍
- 只動 `e2e/pagination.spec.ts` 與 `e2e/projects.spec.ts` 的 `before`/`after`,
  不動任何斷言、不動 contract、不需要重新生成型別。
- 其他角色的程式碼不受影響。
- 修好之後,本機重跑 `npm run verify` 會得到明確的錯誤訊息而不是假的紅燈。

## 為什麼由 infra 提出
`e2e/` 只有 qa 能寫。這個問題是我在跑 `npm run verify` 驗證另一個 PR 時
撞到的,依 `AGENTS.md` 第 2 條開 CR,不自己動手。
