# CR-017: verify 的順序讓 check:boundaries 那段好診斷永遠跑不到

- **提出者**: architect
- **狀態**: proposed
- **阻擋任務**: 無

> 不阻擋任務。這份 CR 要修的不是一個壞掉的檢查 —— `check-boundaries.mjs` 的診斷
> 寫得很好,好到它把兩種可能、以及該怎麼確認都寫出來了。**問題是沒有人看得到它。**
> `verify` 的順序讓另一段程式先失敗,而那段失敗什麼都沒說。

## 問題

`package.json:20`:

```
"verify": "pnpm test:scripts && pnpm check:drift && pnpm check:cr && pnpm check:pits
           && pnpm check:ac && pnpm typecheck && pnpm check:boundaries && pnpm test:e2e"
```

`typecheck` 在 `check:boundaries` **之前**。而 `check:boundaries` 會在
`e2e/` 與 `frontend/src/` 底下建立 `*.boundary-fixture.ts`,用完由 `finally` 刪掉。

被硬殺時 `finally` 跑不到,fixture 就留在原地。`e2e/tsconfig.json` 的
`"include": ["**/*.ts"]` 會把它掃進去,於是**下一次 `pnpm verify` 死在 typecheck**:

```
e2e/ghost.boundary-fixture.ts(1,21): error TS2307: Cannot find module '@af/backend'
```

然後 `&&` 短路,`check:boundaries` 永遠沒有機會執行 —— 而它裡面躺著這段:

```
❌ e2e/ghost.boundary-fixture.ts 已經存在 —— 不覆蓋別人的檔案。
   兩種可能:同一個目錄裡有另一個 check:boundaries 正在跑(fixture 是共用的檔案,
   不同角色各自的 worktree 不會互撞,同一個目錄跑兩次會),或是上一次被硬殺留下的
   殘留物。確認是後者再刪掉重跑。
```

**答案一直都在,只是排在問題後面。**

### 實例(我昨天撞到的)

| | |
|---|---|
| fixture mtime | `2026-09-03 12:16:59` |
| 我撞到的時間 | `2026-09-04 00:32`(約 12 小時後) |
| worktree | `.claude/worktrees/architect` |
| 症狀 | `pnpm verify` 紅在 typecheck |

**範圍**:單一 worktree 的單一實例,ref 是 f1a40c8。我沒有量它多久發生一次 ——
這份 CR 不主張頻率,只主張「發生時的診斷路徑是壞的」。那一項不需要分母。

## 影響

不改的話,代價不是「偶爾要手動刪個檔案」,是**那次除錯會很久**,而且會久在錯的地方。

下一個人看到的是這三件事的組合:

1. `pnpm verify` 紅了
2. `git status` **乾淨** —— fixture 被 `.gitignore:13` 的 `*.boundary-fixture.ts` 蓋住
3. 錯誤指向一個他**沒寫過、也看不見**的檔案,而且訊息是「找不到模組 `@af/backend`」

第 3 點最傷:那個錯誤訊息會把人推向**完全錯誤的方向** —— 去查 workspace 連結、
`tsconfig` 的 `paths`、`pnpm install` 是不是壞了。那些全都沒問題。
這跟 CR-013 描述的「紅的是六條無辜的 AC,真正的原因在輸出更上面」是同一個形狀:
**症狀出現的位置離原因很遠,而中途沒有任何東西把人導回去。**

而這個 repo 已經有一段話寫得剛剛好能把人導回去,只是排在後面。

## 建議變更

兩個修法,可以只做第一個,但第二個才是根治。**都在 infra 的 scope。**

### 一、把 `check:boundaries` 排到 `typecheck` 之前(最小修法)

```
... && pnpm check:ac && pnpm check:boundaries && pnpm typecheck && pnpm test:e2e
```

殘留存在時,`verify` 一樣會紅,但**紅在那段說得清楚的訊息上**,而不是裸的 TS2307。
一行改動,零風險 —— 兩者之間沒有依賴關係,誰先跑都不影響對方的判定。

順帶一個附帶好處:邊界是**結構性**的檢查,型別是**內容**的檢查。結構壞掉時先報結構,
比先報一堆型別錯誤合理。

### 二、建立 fixture 前清掉夠舊的同名殘留(根治)

現在的行為是**拒絕覆寫並退出**,那個保守是對的 —— 它保護的是「同一個目錄裡有另一個
`check:boundaries` 正在跑」。但那個情境的 fixture 只會有**幾秒鐘**大,而殘留物是
**幾小時到幾天**。用 mtime 分得開:

- 夠新(例如一分鐘內)→ 維持現狀,拒絕並印出現在那段訊息
- 夠舊 → 自己清掉、繼續跑,並印一行說「清掉了一個 <時間> 前的殘留」

門檻多少由 infra 定,我沒有數字。

## 被否決的方案

**在 `e2e/tsconfig.json` 排除 `*.boundary-fixture.ts`。** 這是三個裡面看起來最乾淨的
——讓殘留對 `typecheck` 徹底無害,而不是調整看到它的順序。**我試著論證它,然後發現
它會把檢查自己弄壞。**

`scripts/check-boundaries.mjs:57,66` 的三個 case 跑的是 `tsc -p e2e/tsconfig.json`
—— **跟 `pnpm typecheck` 同一份設定**。把 fixture 排除掉,`check:boundaries` 就不會
編譯它,等不到預期的 `TS2307`,於是報「意外通過」(那正是該檔案第 20 行的檔頭警告
特別點名的失敗模式:*tsc 意外通過時,要先分清楚是設定壞了還是環境洩漏*)。

**這個方案把「檢查會誤判」換掉「診斷難讀」,是更差的交易。** 寫在這裡是因為下一個
想修這件事的人多半也會先想到它。

## 波及範圍

- **infra** —— `package.json`(第一項,一行)、`scripts/check-boundaries.mjs`(第二項)。
  兩者都是 infra 的路徑。
- **contract** —— 無。
- **其他角色** —— 無程式變更。受益者是所有在本機跑 `pnpm verify` 的人。
- **CI** —— 無影響。每個 job 是乾淨 checkout,不會有殘留(這也是為什麼這個缺陷
  **只在人的機器上發生**,跟 CR-013 的 port 競態一樣)。

## 為什麼是 CR 而不是坑註解或訊息

`package.json` 與 `scripts/` 都不是 architect 能寫的(ADR-003),所以不能就地留註解。

依 ADR-009 第二問,下一個踩到的人在看什麼?他在看 `pnpm verify` 的輸出 ——
而**這份 CR 要求的變更就是去改那個輸出**。知識的家與修法的家在這裡剛好重合,
所以不需要額外的坑註解:第一項改完,那段診斷自己就是註解。

也不用訊息:ADR-009:164,訊息可以通知不能保存,而這件事要等 infra 有空才會做。
