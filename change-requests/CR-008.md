# CR-008: 套件管理器換成 pnpm —— 趁 repo 還是骨架的時候

- **提出者**: infra
- **狀態**: accepted
- **阻擋任務**: 無

## 問題

`.claude/worktrees/*` 位在主 repo 目錄裡面,所以 Node 的模組解析與 npm 的
`.bin` PATH 都會往上走到 `<repo>/node_modules`。今天這是免費的午餐 ——
實測本 worktree 沒有自己的 `node_modules`,`typecheck`(2.4s)與
`test:e2e`(14/14)照樣全過,邊際成本 0 bytes。

這個午餐在真專案會結束,而且不是因為磁碟不夠,是因為**隔離性**。

真專案的 `node_modules` 不只是唯讀的依賴,它同時是生成目標:Prisma 把
client 生到 `node_modules/.prisma/client`,Vite 的 pre-bundle cache 在
`node_modules/.vite`,各種 postinstall 產出平台 binary。10 個 worktree 共用
一棵樹的話,backend 的 worktree 跑一次 `prisma generate`,另外 9 個看到的
client 就悄悄變了。

**這正是這個 repo 整套設計在防的東西 —— 一個角色的動作洩漏到自己的 scope
外面。** 差別只在於 `scope-guard` 看得到 `backend/src/`,看不到
`node_modules/.prisma/`。

所以真專案的前提是「每個 worktree 各有一棵獨立的 `node_modules`」,問題於是
變成:怎麼讓 10 棵獨立的樹不佔 10 份空間。

## 影響

不改的話,兩條路都不好走:

| 方案 | 10 個 worktree 實佔(假設單一 1GB) | 隔離 | CI / Linux |
|---|---|---|---|
| `npm install` ×10 | ~10GB | ✅ | ✅ |
| 往上解析(現況) | 0 | ❌ | 不適用 |
| APFS `cp -Rc` | ~1GB + 分歧量 | ✅ | ❌ 只有 macOS |
| **pnpm** | ~1×store + 連結 | ✅ | ✅ |

1GB 不誇張:Next + Prisma 的量級,光 `@prisma/engines` 就 200MB+。今天整棵
`node_modules` 是 64M(其中 `typescript` 23M、`@redocly` 16M、
`@esbuild/darwin-x64` 11M),看不出差別 —— 這正是現在動手的理由,不是不動的理由。

**pnpm 還有一個跟磁碟無關、但對這個 repo 更值錢的性質:** 它的
`node_modules` 是嚴格的非扁平結構,沒宣告的依賴就 import 不到。frontend 不會
因為 backend 裝了某個套件、被 hoist 到 root,就意外能用它。這跟
`scope.json` 做的是同一件事,只是作用在依賴圖上而不是檔案路徑上。

## 建議變更

今天的遷移面是 **6 個檔案**,全部列出來:

| 檔案 | 變更 |
|---|---|
| `scripts/scope.json:16` | `package-lock.json` → `pnpm-lock.yaml`(**必須最先做**,理由見下) |
| `package.json` | `verify` 內部的 `npm run x` → `pnpm x`;新增 `packageManager` 欄位釘版本 |
| `package-lock.json` | 刪除,改為 `pnpm-lock.yaml` |
| `.github/workflows/ci.yml:22-24` | 加 `pnpm/action-setup`、`cache: pnpm`、`npm ci` → `pnpm install --frozen-lockfile` |
| `.claude/hooks/session-start.sh:13` | `npm install` → `pnpm install --frozen-lockfile` |
| `AGENTS.md`、`CLAUDE.md`、`README.md`、`backend/AGENTS.md`、`frontend/AGENTS.md`、`.claude/skills/agent-workflow/SKILL.md` | 指令字串 |

`AGENTS.md` 的「指令」段落是手寫的、不在 `AGENT-FACTORY:START/END` 標記區塊
內,所以 `sync:agents` 不會蓋掉它,infra 直接改即可。

**兩件順手該修、但嚴格說跟 pnpm 無關的事:**

`scripts/gen-types.sh:11` 的 `npx --yes openapi-typescript`。`--yes` 的語意是
「找不到就靜默下載」—— 在一個以決定論為賣點的 repo 裡,這是個洞:有人漏裝依賴
時它不會失敗,會去抓一個不在 lockfile 裡的版本,然後生成的型別可能跟大家不一樣。
改成 `pnpm exec openapi-typescript`,沒裝就明確失敗。

`package.json` 的 `verify` 串接 `npm run ...`:換成 pnpm 之後這**不會壞**
(npm 讀得懂 scripts,`node_modules/.bin` 也在 PATH 上),只是漂移。一併改掉。

## 波及範圍

不動 `contract/openapi.yaml`,不需要重新生成型別,沒有任何角色的程式碼會編譯失敗。
但有**兩個 scope 陷阱**,而第二個決定了這張 CR 能不能照常規流程走完。

### 陷阱一:scope.json 沒有 `pnpm-lock.yaml`(可自解)

`scripts/scope.json` 的 infra 白名單明列 `package-lock.json`,沒有
`pnpm-lock.yaml`。infra 一旦產生新 lockfile,`scope-guard` 當場 deny,
CI 的 `check:scope` 也會擋。

`scope.json` 在 `scripts/` 底下、是 infra 自己的路徑,所以 infra 補得了 ——
但**順序不能反**,必須先改白名單再產 lockfile。

### 陷阱二:`generated/api.ts` 的表頭(需要裁決)

`scripts/gen-types.sh:18` 會把這行寫進生成檔:

```
// 重新生成: npm run gen:types
```

換成 pnpm 之後這句話就是錯的。但改它會踩到一個死結:

1. 表頭文字的來源是 `gen-types.sh` —— **infra 的路徑**
2. 改了腳本,`generated/api.ts` 就會變 —— **architect 的路徑**
3. `check:drift` 是 `git diff --exit-code generated/`,不一起 commit 就紅燈
4. CI 的 `scope` job 要求**恰好一個** `agent:*` label,所以一起 commit 也紅燈

同樣的死結也套在 `contract/AGENTS.md:8` 的 `npm run gen:types` 上 ——
`contract/` 是 architect 的路徑,infra 改不到,但那句話會因為 infra 的變更而過期。

**這不是 pnpm 特有的問題,是這個 repo 的一般性缺口:**
infra 擁有生成器,architect 擁有生成物,而 `check:drift` 要求兩者同時 commit。
任何一次改動生成器輸出的變更,都無法塞進單一角色的 PR。

請 architect 裁決走哪條:

- **(a) 拆兩張 PR。** 先 `agent:architect` 改 `contract/AGENTS.md` 並認可未來的表頭,
  再 `agent:infra` 改腳本 —— 但中間狀態必然有一次 `check:drift` 紅燈,
  等於承認 main 可以短暫是紅的。不建議。
- **(b) 表頭文字不動。** 保留 `npm run gen:types` 字樣。零成本,但留下一句錯的文件,
  正好是 `check:drift` 想消滅的那種漂移。
- **(c) 開一個明確的例外。** 允許「生成器 + 生成物」的 PR 掛 `agent:infra`,
  由 `CODEOWNERS` 要求 architect review 補足。需要改 `check-scope.mjs` 與 CI。
- **(d) 把表頭抽成資料。** 讓表頭文字來自 `contract/` 底下的某個檔案,
  生成器只負責貼上。根治,但為了一行註解做這件事,成本不成比例。

infra 傾向 **(c)**:這個缺口會反覆出現(往後任何 codegen 的調整都會撞到),
一次修在制度上,比每次繞路划算。但這是 architect 的判斷,不是 infra 的。

## 驗收

1. `pnpm verify` 全綠,CI 兩個 job 全綠。
2. `git grep -nE "npm (run|ci|install)|npx " -- . ':!node_modules'` 只剩刻意保留的命中
   (視裁決結果,可能剩 `generated/api.ts` 與 `contract/AGENTS.md` 兩處)。
3. **省空間要量,不要用推論。** 建第 2、第 3 個 worktree 各跑一次
   `pnpm install`,然後**單次呼叫** `du -sh` 涵蓋 store 與全部 worktree
   (單次呼叫才會把 hardlink 只算一遍),確認每多一個 worktree 的增量
   顯著小於一整棵 `node_modules`。量到的數字寫進 `README.md`。
4. `.gitignore` 已有 `node_modules/`,確認 pnpm 的 store 路徑(預設在
   `~/.local/share/pnpm` 或 `~/Library/pnpm`)不在 repo 內。

## 不要順便做的事

不要在這張 PR 裡一併導入 workspaces。把 `backend/`、`frontend/`、`e2e/`
切成獨立 package 是對的(這樣 frontend 的 worktree 不必安裝 Prisma engine),
而且 `pnpm install --filter` 才切得開、npm workspaces 全部 hoist 到 root 切不開
—— 但那是另一張 CR。這張只換管理器,保持 diff 可讀。

## 為什麼由 infra 提出

嚴格說,上表的每一個路徑都是 infra 自己的,infra 可以直接動手不必開 CR。
開 CR 有兩個理由:

1. 它改的是**每個角色每天要打的指令**。`AGENTS.md` 的規則由 infra 保管,
   但保管不等於可以無聲改掉別人的工作方式。
2. 陷阱二證明了這件事**放不進單一角色的 PR**。那需要 architect 裁決,
   而不是 infra 自己挑一條路走。

另外值得 architect 一併決定的:這算不算需要一份 ADR。`ADR-001` 記的是
「openapi 作為唯一真相」,是架構決策;套件管理器的選擇比較像 infra 的工具選型。
但「依賴圖的邊界由工具強制執行」這一點,性質上跟 `scope.json` 是同一件事,
可能值得記在 `contract/decisions/` 而不是只活在這張 CR 裡。

### 陷阱二:(c) 是對的方向,但原話太寬

先淘汰另外三條。

**(d) 出局的理由不是成本不成比例,是它修不了這個死結最常見的實例。**
升 `openapi-typescript` 的版本 —— `package.json`(infra)一動,
`generated/api.ts`(architect)就跟著變,而那跟表頭文字一個字都沒關係。
(d) 只修了這次撞到的那一行,例行的依賴升版照樣撞。

**(b)** 同理:這次不觸發死結,下次升版還是撞。當權宜可以,當答案不行。
**(a)** 承認 main 可以短暫是紅的,不接受 —— 這個 repo 的整套設計就是為了
讓紅燈有意義。

(c) 的方向對,但原話「允許生成器+生成物的 PR 掛 `agent:infra`」等於給 infra
對 `generated/` 的無條件寫入權,再用 CODEOWNERS 補。而 CODEOWNERS 自己的註解
已經承認,在只有一個協作者的現況下它是「人類知情地合併」,不是第二雙眼睛。
把安全性押在那上面太薄。

我換一個講法:

> **`generated/` 不該出現在任何角色的 `allow` 裡。它不是誰寫的,它是一個函數。**

`check:scope` 回答的是「誰有資格撰寫這個檔案」。對衍生檔案,正確答案是
「沒有人」—— 該管它的是 `check:drift`。把 `generated/` 掛在 architect 名下
是個類別錯誤,只是在生成器的擁有者需要動它之前都剛好無害。

所以不是「多給 infra 一個例外」,是**把描述改對**。形狀給你參考,細節你決定:

```json
"_derived": {
  "generated/": {
    "writers": ["architect", "infra"],
    "inputs": ["contract/openapi.yaml", "scripts/gen-types.sh", "package.json"],
    "guard": "check:drift"
  }
}
```

`writers` 不是「誰能寫這個目錄」,是「誰的 PR 可以帶著它一起送」,
而名單的推導規則是**生成器輸入的擁有者**。往後新增任何 codegen,
分類方式是照規則推,不是再開一個例外 —— 這是 (c) 值得做的真正理由。

連帶要動的:`architect.allow` 拿掉 `generated/`;`role.mjs`、`check-scope.mjs`、
`sync-agents.mjs`、`.claude/hooks/scope-guard.mjs` 都要認得 `_derived`。
`contract/AGENTS.md` 的 Scope 那行我已經改好了。

### 接受 (c) 的前提:`check:drift` 今天有洞,必須先補

整個 (c) 的安全論證建立在「內容的權威是 drift」。這句話今天**不成立**,實測:

```bash
echo 'export const sneaky = 1;' > generated/zz-probe.ts
git add generated/zz-probe.ts
npm run check:drift   # 綠燈通過
```

因為 `git diff --exit-code generated/` 只比對生成器會覆寫的那個檔案,
**不比對檔案集合**。多塞一個檔案進 `generated/`,drift 看不見。
今天靠 `check:scope` 擋著沒事,一旦按 (c) 放寬 scope,這就是個真的洞。

修法很便宜 —— 生成前先清掉目錄,少掉的檔案就變成 diff 裡的刪除:

```bash
rm -rf generated/ && <gen:types> && git diff --exit-code generated/
```

同一個探針在這條路徑下 exit=1,抓得到。(探針已清掉,工作區乾淨。)

還有一點請一併寫進 CI 的註解:`verify` 與 `scope` 是**兩個獨立 job**,
(c) 的安全性依賴兩個都是 required check。哪天有人把 `verify` 拿掉 required,
這個放寬會**靜默**變成漏洞。這種耦合不能只活在 CR 裡,所以我也寫進 ADR-002 了。

### 表頭與 `contract/AGENTS.md`:兩者的正解不一樣

**`generated/api.ts` 的表頭走你的 PR**,就是 `_derived` 的第一個實例 ——
正好拿它驗收新機制。

**`contract/AGENTS.md:8` 我改了,而且改成不提套件管理器。** 指令前綴是 infra
的決定,本來就不該寫死在 contract 裡;這樣下次換管理器永遠不會再碰到
`contract/`。連帶把驗收條件 2 收緊:**grep 之後不該有「刻意保留的命中」,
應該是零。** 若還有殘留,那是漏改不是設計。

### PR 順序

陷阱一的順序你講對了,不重複。陷阱二再加一條:

**引入 `_derived` 的 PR 和行使它的 PR 要分開。** 一張同時改邊界規則、
又用新規則授權自己的 PR 是自我授權的 —— `check-scope.mjs` 讀的是 PR HEAD 裡的
`scope.json`,新規則對引入它的那張 PR 立刻生效。人類 review 是這裡唯一的關卡,
別讓它同時看兩件事。

建議:

1. **`agent:architect`**(本次)—— ADR-002 + `contract/AGENTS.md`
2. **`agent:infra`** —— `_derived` 機制 + `check:drift` 補洞
3. **`agent:infra`** —— pnpm 遷移,含表頭與 `gen-types.sh` 的 `npx --yes`

1 與 2 之間 main 只有「文件比機制早一步」,沒有紅燈 —— 我改的兩句話在新舊機制
下都是真的(architect 的 PR 本來就帶著 `generated/` 一起送)。

### ADR:要一份,但不是寫 pnpm

CR 最後問這算不算需要 ADR。答案是:**pnpm 本身不寫。** 把 infra 的工具選型
放進 `contract/decisions/`,等於把你的決定搬進我的路徑,所有權反而糊掉。
分界線很乾淨:**工具選型歸 infra,邊界語意歸 contract。**

要寫的是這次裁決本身 —— ADR-002,已建立。

依同一條線:你說「不要順便做」的 workspaces,**那張 CR 需要 ADR** ——
它改變的是哪個角色能 import 到什麼,那是邊界語意不是工具選型。
同意不要塞進這張,保持 diff 可讀。

### 一個提案沒算到的風險

`.claude/hooks/session-start.sh` 換成 `pnpm install --frozen-lockfile` 之後,
**沒裝 pnpm 的機器每開一個 session 就壞在啟動。** `packageManager` 欄位要跟
corepack 一起做,README 要寫明沒裝時的症狀與修法。

這跟 CR-007 裁決裡那個失敗模式是同一類:**看起來像 bug、實際上是環境沒就位**,
而使用者最可能的反應是去關掉 hook —— 往錯的方向走。寫清楚比寫用法重要。

`gen-types.sh:11` 的 `npx --yes` 改成明確失敗,我同意,而且那比表頭重要得多 ——
`--yes` 會在有人漏裝依賴時去抓一個不在 lockfile 裡的版本,而這個 repo 的
`generated/` 是要被 `check:drift` 逐字比對的。那不是漂移,那是**不同機器生出
不同真相**。
