# CR-013: e2e 的 port 窗口關不掉 —— 要 backend 自己選 port 再回報

- **提出者**: qa
- **狀態**: accepted
- **阻擋任務**: 無

> 不阻擋任何任務。但它每一次發作都會弄紅一張**與 e2e 無關的 PR**,而最順手的
> 反應是「再跑一次就好」—— 那正是把 e2e 紅燈訓練成雜訊的路徑。

## 問題

`e2e/server.ts` 的 `startServer()` 目前這樣拿 port:

1. `net.createServer().listen(0)` 跟 OS 要一個空的 port
2. 關掉它
3. `spawn` backend,用環境變數 `PORT` 把那個號碼交給它
4. backend 綁上去

**第 2 步與第 4 步之間有一個窗口。** 那個 port 在這段期間對任何人都是空的,
包含同一台機器上另一個 `pnpm verify` 的 `listen(0)`。兩邊拿到同一個號碼,
一邊綁到、另一邊 `EADDRINUSE`。

這不是新發現 —— `server.ts` 的檔頭在 #82 當下就寫了「**這不是零**」。當時的判斷是
「以目前的機率不值得」開 CR。**這張 CR 帶的是那個判斷缺的東西:機率。**

### 它長什麼樣子

```
failureType: 'hookFailed'
Error: listen EADDRINUSE: address already in use :::49565
...
not ok 1 - AC-008: 設有 ownerEmail 的專案狀態異動後...
  failureType: 'cancelledByParent'
# pass 45  fail 0  cancelled 6      exit=1
```

`before()` 綁不到 port → 那個 describe 的 subtest 一條都沒跑 → 全部 cancelled,
而 **`fail` 是 0 正因為沒有任何斷言執行過**。

這個外觀很傷:紅的是六條無辜的 AC,而真正的原因在輸出的更上面。第一次看到的人
會去讀 `AC-008` 的斷言,那裡什麼問題也沒有。infra 就是這樣撞到的 —— 它那張 PR
只動 `.md`。

### 分母

| 誰 | 量的是哪條指令 | 命中 |
|---|---|---|
| infra | 做別的事時順手撞到(條件未受控) | 約 1 / 8 |
| architect | 閒置連跑 `pnpm verify` | 0 / 10 |
| architect | 4 個 `pnpm verify` 並行 | 1 / 12,接著 0 / 16 |
| qa | 4 個 `test:e2e` 並行 | 1 / 64 |

**這幾列不能相加。** `verify` 一次要跑七段、單次時間長好幾倍,`test:e2e` 只有測試 ——
每次 run 暴露在窗口下的時間不同,命中率不可比。能說的是量級:
**並行時是百分之個位數,閒置 0 / 10 沒見過。**

一句話要說清楚:**「並行就能重現」不成立**。那是第一次 1/12 之後的推論,再跑 16 次
0 命中就塌了。站得住的只有「閒置時沒見過」與「並行時約 2%」。

## 影響

不改的話,代價不是「測試偶爾紅」,是**紅燈的意義被稀釋**。

這台機器同時開五個角色 session。任兩個在重疊時間跑 `verify`,約 2% 的機率其中一邊
會紅在自己沒動過的檔案上。2% 低到不會逼人處理,又高到每隔幾天就發生一次 —— 這是
最壞的區間:**它會訓練出「e2e 紅了先重跑」的反射**,而那個反射會一併吃掉真正的紅燈。

CI 不會發現這件事:每個 job 是獨立容器,沒有第二個 run 跟它搶 port。所以這個缺陷
**只在人的機器上發生,而且只在人趕時間的時候發生**。

qa 這一側能做的已經做完了。`assertPortFree()` 留著、窗口從整段測試縮到毫秒級 ——
剩下的窗口在「誰來決定 port」這件事上,而那個決定權在 backend。

## 建議變更

**讓 backend 自己選 port,再把實際綁到的號碼回報出來。** 兩步都在 `backend/src/`:

1. `PORT=0`(或不給 `PORT`)時,`app.listen(0)` 讓 OS 在**綁定的當下**指派 ——
   窗口消失,因為選擇與綁定是同一個系統呼叫。
2. 綁定成功後把實際 port 印到 stdout,一行、固定格式,例如:

```
listening on 51423
```

`e2e/server.ts` 改成:不再預先挑 port,`spawn` 之後讀 stdout 等那一行,拿到號碼再
組 base URL。目前 stdout 是 `'ignore'`,要改成 `'pipe'` —— 那是我的檔案,我來改。

**為什麼不是「重試幾次」。** 撞到 `EADDRINUSE` 就換一個 port 重試,能把 2% 壓到
接近 0,而且完全在 e2e/ 裡做得完、不需要這張 CR。我不建議它,兩個理由:
它把一個**可以消除**的競態變成一個**被容忍**的競態;而且重試會讓「真的有人佔住那個
port」與「我們自己撞自己」再一次變成同一種現象 —— 那正是 CR-004 當初要拆開的東西。

## 波及範圍

- **backend** —— `backend/src/index.ts` 的啟動段。`PORT` 有值時行為不變,只有
  `PORT=0` 或未設時才走新路徑,所以 `pnpm dev:backend` 與部署不受影響。
- **e2e** —— `server.ts` 的 `startServer()`。七個 spec 都經由它拿 `base`,
  介面不變,改的是它內部怎麼得到那個號碼。這是我的路徑,裁決後我送。
- **infra** —— 沒有。`.env.example` 若寫了 `PORT=3000` 照舊有效。
- **contract** —— 沒有。port 不是 API 的一部分。

## 一個我沒有選的更小修法

`server.ts` 可以在 `spawn` 之前**不關掉**那個 `listen(0)` 的 socket,改用
`SO_REUSEPORT` 之類的方式交棒。試不通:Node 沒有把那個選項開出來,而且就算開得出來,
「兩個行程同時綁同一個 port」本身就是另一種混淆的來源。**窗口的根源是「選 port 的人
不是綁 port 的人」,只有讓它們變成同一個人才會歸零。**

---
## Architect 裁決

**accepted,但帶四項修正。** 沒有 contract 變更 —— port 不是 API 的一部分,
`openapi.yaml` 與 `tasks.yaml` 都不動,沒有版本要註明。

診斷我完全同意,而且那句話是這份 CR 最值錢的地方:

> **窗口的根源是「選 port 的人不是綁 port 的人」,只有讓它們變成同一個人才會歸零。**

那是 TOCTOU 的一般形式。`listen(0)` 之所以能歸零,不是因為它比較快,是因為
**選擇與綁定變成同一個系統呼叫** —— 不存在「已選但未綁」的中間狀態可以被別人插進來。
「重試幾次」被否決的理由也對:它把一個可以**消除**的競態改成一個被**容忍**的競態,
而且會讓「別人佔住 port」與「我們自己撞自己」再度合流,那正是 CR-004 拆開的東西。

以下四項是實作前必須先對齊的,前兩項是**修正 CR 的原文**,後兩項是**加上去的條件**。

### 一、只有 `PORT=0` 走新路徑。「不給 PORT」那半邊我否決

CR 寫的是「`PORT=0`(**或不給 `PORT`**)時」。後半會弄壞現況:

```
backend/src/index.ts:26   const port = Number(process.env.PORT ?? 3000);
```

**不給 `PORT` 現在是 3000**,`pnpm dev:backend` 與 `.env.example` 的 `PORT=3000`
都依賴這個預設。改成「未設 → `listen(0)`」會讓開發用的 server 每次跑到隨機 port。

CR 的「波及範圍」寫著「`pnpm dev:backend` 與部署不受影響」—— 那個結論是對的,
但只有在**未設 `PORT` 保持 3000** 的前提下才成立。原文的括號與自己的波及範圍矛盾,
以波及範圍為準。

### 二、不要發明第二種 stdout 格式,改既有那一行

CR 提議印 `listening on 51423`。但 `index.ts:30` **已經在印**:

```
backend listening on :${port}
```

問題不是缺一行,是**那一行印的是「要求的」port 而不是「實際綁到的」**。
`listen(0)` 時該變數是 0,現況會印出 `backend listening on :0`。

所以:**保留既有訊息的形狀,改成印真正綁到的號碼**,從 `server.address().port` 取,
不要新增第二行。理由是新增格式會有兩行都宣稱是 port,而其中一行是錯的 ——
這正是 `server.ts` 檔頭那段「讓兩種現象變成同一種」在講的事。qa 解析既有那一行。

### 三、等不到那一行必須快速失敗,不能無限等

這一項 CR 沒有寫,而它是 accepted 的條件。

現在的失敗是 `EADDRINUSE`,難看但**會停、有訊息**。改成「讀 stdout 等一行」之後,
如果 backend 在印出之前就死了,天真的實作會**永遠等下去** —— 那是把一個 2% 的吵鬧
失敗換成一個偶發的**安靜掛住**,而安靜的失敗這個 repo 已經判過三次死刑
(`server.ts` 檔頭那三道防線、CR-004、ADR-009 的「沒有消費者」)。**那是更差的交易。**

要求:等待要有 timeout,逾時或行程先死時把 `state.stderr` 一起吐出來。
`ProcState.died` 已經在那裡了,接上去即可。

順帶一個好處值得寫下來:讀到那一行**同時證明了綁定成功**,比現在「spawn 完就假設它起來了」
強 —— 這一項不只是防呆,是把 CR 的收益再擴大一點。

### 四、那一行從此是跨角色介面,要留坑註解

`listen` 的那行 log 一旦被 `e2e/server.ts` 解析,它就不再是給人看的訊息,
而是 **backend 與 e2e 之間的介面**。而 backend 改不到 `e2e/`、也不會跑 qa 的測試 ——
**它有能力靜默地弄壞 e2e,而且不會有任何東西告訴它。**

依 ADR-009 第二問(他再踩的時候眼睛在看什麼),家在 print 的那一行旁邊:

```ts
// 坑(下一個踩的人:qa):這一行的格式是 e2e/server.ts 解析的介面,改字要一起改
```

這是 accepted 的條件之一,不是建議。

### 順序:backend 先,qa 後

qa 的解析在 backend 印出真實 port 之前會失敗,所以**不能同時送**。
兩份也不能合成一張 PR —— 不同角色、label 只能掛一個。

1. **backend** 改 `backend/src/index.ts`(第一、二項 + 第四項的坑註解),送 PR、合併
2. **qa** 再改 `e2e/server.ts`(`stdio` 開 stdout、解析、第三項的 timeout),送 PR

### 一句給下一個讀這份 CR 的人

那張「分母」表是這份 CR 最該被模仿的部分。它**拒絕把四列相加**(暴露時間不同、不可比),
而且在下一段親手推翻自己「並行就能重現」的推論 —— 1/12 之後再跑 0/16 就塌了。
`agent-workflow` skill §5 的「一次重現不是重現方法」講的就是這個,而這份 CR 是它的實例。

**保留下來的結論只有兩句:閒置時 0/10 沒見過,並行時約 2%。** 那兩句撐得住,
而且足以支持這次的變更 —— 不需要更精確的數字,因為修法是把機率歸零,不是壓低。
