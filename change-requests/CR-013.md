# CR-013: e2e 的 port 窗口關不掉 —— 要 backend 自己選 port 再回報

- **提出者**: qa
- **狀態**: proposed
- **阻擋任務**: 無

> 不阻擋任何任務。但它每一次發作都會弄紅一張**與 e2e 無關的 PR**,而最順手的
> 反應是「再跑一次就好」—— 那正是把 e2e 紅燈訓練成雜訊的路徑。

## 問題

`e2e/server.ts` 的 `startServer()` 目前這樣拿 port:

1. `net.createServer().listen(0)` 跟 OS 要一個空的 port
2. 關掉它
3. `spawn` backend,用環境變數 `PORT` 把那個號碼交給它
4. backend 綁上去

**第 2 步與第 4 步之間有一個窗口。** 那個 port 在這段期間對任何人都是空的,
包含同一台機器上另一個 `pnpm verify` 的 `listen(0)`。兩邊拿到同一個號碼,
一邊綁到、另一邊 `EADDRINUSE`。

這不是新發現 —— `server.ts` 的檔頭在 #82 當下就寫了「**這不是零**」。當時的判斷是
「以目前的機率不值得」開 CR。**這張 CR 帶的是那個判斷缺的東西:機率。**

### 它長什麼樣子

```
failureType: 'hookFailed'
Error: listen EADDRINUSE: address already in use :::49565
...
not ok 1 - AC-008: 設有 ownerEmail 的專案狀態異動後...
  failureType: 'cancelledByParent'
# pass 45  fail 0  cancelled 6      exit=1
```

`before()` 綁不到 port → 那個 describe 的 subtest 一條都沒跑 → 全部 cancelled,
而 **`fail` 是 0 正因為沒有任何斷言執行過**。

這個外觀很傷:紅的是六條無辜的 AC,而真正的原因在輸出的更上面。第一次看到的人
會去讀 `AC-008` 的斷言,那裡什麼問題也沒有。infra 就是這樣撞到的 —— 它那張 PR
只動 `.md`。

### 分母

| 誰 | 情境 | 命中 |
|---|---|---|
| infra | 做別的事時順手撞到 | 約 1 / 8 |
| architect | 閒置連跑 | 0 / 10 |
| architect | 4 個 `verify` 同時跑 | 1 / 12,接著 0 / 16 |
| qa | 4 個 `test:e2e` 同時跑 | 1 / 64 |

**並行合計 2 / 92 ≈ 2%,閒置 0 / 10。**

一句話要說清楚:**「並行就能重現」不成立**。那是第一次 1/12 之後的推論,再跑 16 次
0 命中就塌了。站得住的只有「閒置時沒見過」與「並行時約 2%」。

## 影響

不改的話,代價不是「測試偶爾紅」,是**紅燈的意義被稀釋**。

這台機器同時開五個角色 session。任兩個在重疊時間跑 `verify`,約 2% 的機率其中一邊
會紅在自己沒動過的檔案上。2% 低到不會逼人處理,又高到每隔幾天就發生一次 —— 這是
最壞的區間:**它會訓練出「e2e 紅了先重跑」的反射**,而那個反射會一併吃掉真正的紅燈。

CI 不會發現這件事:每個 job 是獨立容器,沒有第二個 run 跟它搶 port。所以這個缺陷
**只在人的機器上發生,而且只在人趕時間的時候發生**。

qa 這一側能做的已經做完了。`assertPortFree()` 留著、窗口從整段測試縮到毫秒級 ——
剩下的窗口在「誰來決定 port」這件事上,而那個決定權在 backend。

## 建議變更

**讓 backend 自己選 port,再把實際綁到的號碼回報出來。** 兩步都在 `backend/src/`:

1. `PORT=0`(或不給 `PORT`)時,`app.listen(0)` 讓 OS 在**綁定的當下**指派 ——
   窗口消失,因為選擇與綁定是同一個系統呼叫。
2. 綁定成功後把實際 port 印到 stdout,一行、固定格式,例如:

```
listening on 51423
```

`e2e/server.ts` 改成:不再預先挑 port,`spawn` 之後讀 stdout 等那一行,拿到號碼再
組 base URL。目前 stdout 是 `'ignore'`,要改成 `'pipe'` —— 那是我的檔案,我來改。

**為什麼不是「重試幾次」。** 撞到 `EADDRINUSE` 就換一個 port 重試,能把 2% 壓到
接近 0,而且完全在 e2e/ 裡做得完、不需要這張 CR。我不建議它,兩個理由:
它把一個**可以消除**的競態變成一個**被容忍**的競態;而且重試會讓「真的有人佔住那個
port」與「我們自己撞自己」再一次變成同一種現象 —— 那正是 CR-004 當初要拆開的東西。

## 波及範圍

- **backend** —— `backend/src/index.ts` 的啟動段。`PORT` 有值時行為不變,只有
  `PORT=0` 或未設時才走新路徑,所以 `pnpm dev:backend` 與部署不受影響。
- **e2e** —— `server.ts` 的 `startServer()`。七個 spec 都經由它拿 `base`,
  介面不變,改的是它內部怎麼得到那個號碼。這是我的路徑,裁決後我送。
- **infra** —— 沒有。`.env.example` 若寫了 `PORT=3000` 照舊有效。
- **contract** —— 沒有。port 不是 API 的一部分。

## 一個我沒有選的更小修法

`server.ts` 可以在 `spawn` 之前**不關掉**那個 `listen(0)` 的 socket,改用
`SO_REUSEPORT` 之類的方式交棒。試不通:Node 沒有把那個選項開出來,而且就算開得出來,
「兩個行程同時綁同一個 port」本身就是另一種混淆的來源。**窗口的根源是「選 port 的人
不是綁 port 的人」,只有讓它們變成同一個人才會歸零。**
