# CR-014: 兩個機制在「第一次真的被用到」的那一刻才紅 —— 而現在就是那一刻

- **提出者**: qa
- **狀態**: accepted
- **阻擋任務**: 無

> 不阻擋任務,但**擋住每一張 PR**:現在任何人開一份 CR、或留下第一則坑註解,
> `pnpm verify` 都會紅在 `scripts/*.test.mjs`。包括這一份 CR 自己。
>
> 三個問題有同一個形狀:**拿當下的狀態當前提。** 一條斷言 repo 沒有坑,一條依賴
> repo 沒有 proposed 的 CR,還有一條是我寫這份 CR 時犯的 —— 拿 `grep` 的結果當歷史。

## 問題

`scripts/` 裡有兩條測試,它們斷言的是**「這個 repo 今天還沒有人用過這個機制」**,
而不是機制的行為。兩條都在第一次真的被用到時變紅。

我這一輪同時觸發了兩條:開了 CR-013,並依 ADR-009 在 `e2e/server.ts` 留下第一則
坑註解。兩件都是這兩個機制**被設計出來就是要人做的事**。

### 一、`pits.test.mjs:91` —— 斷言「repo 裡沒有坑」

```js
test('現況掃描是乾淨的 —— 文件裡的範例沒有被當成真的坑', () => {
  const pits = scanPits();
  assert.deepEqual(pits, [], `不該有:${JSON.stringify(pits)}`);
});
```

**意圖是對的**:它要擋的是「ADR-009 與 AGENTS.md 裡的示範標記被算成真的坑」那個
假陽性。但寫出來的斷言是「掃描結果是空的」—— 這兩件事只在**還沒有任何真坑**的時候
等價。第一則真的坑註解一寫,它就紅:

```
不該有:[{"file":"e2e/server.ts","line":92,"role":"qa",...}]
```

諷刺的地方是:這條測試守的機制,它的價值**完全來自於有人會去用它**,
而它的斷言說「沒有人用過」。

### 二、`check-cr.test.mjs:127` —— 一條一直空過的接線測試

這條寫得很好,它刻意不寫死數字:

```js
// 不寫死「現在有幾份 proposed」—— 那會讓這條測試在下一張 CR 開出來時就紅,
// 而它要驗的是「接線有沒有接上」,不是 repo 今天的狀態。
```

但它有兩個分支,而**過去一直走的是空的那一支**:

```js
if (proposed.length === 0) {
  assert.doesNotMatch(out, /仍為 proposed/);   // ← 一直是這一支
} else {
  assert.match(out, new RegExp(`${proposed.length} 份 CR 仍為 proposed,...`));
}
```

在 CR-013 之前,所有 CR 都是 accepted,`proposed.length === 0`,測試**恆真通過**。
CR-013 讓它第一次走進另一支,然後抓到了它本來就要抓的東西:`check-cr.mjs` 的輸出裡
沒有那一行,而 `pendingSummary()` 定義了、export 了、有三條單元測試。

### 更正:那條線接上過,是被砍掉的

我第一版寫「CLI 從來沒有呼叫它」,那是錯的。architect 指出來之後我逐 commit 查:

```
$ git grep -c pendingSummary <ref> -- scripts/check-cr.mjs
085925d  2    #78「check:cr 多印一行——還有幾份 CR 在等裁決」   定義 + 呼叫
378d109  1    #91「check:ac 改成推導 status」                   只剩定義
HEAD     1
```

`#78` 接上了:

```js
// 等裁決的 CR。放在最後 push,所以它是提醒列表的最後一行。
const pending = pendingSummary(crs);
if (pending) warnings.push(pending);
```

`#91` 刪掉的是**整段 `warnings` 相關的區塊**(它同時拿掉了「proposed 的 CR 宣稱阻擋
非 blocked 任務」那則鏡像提醒),`pendingSummary` 的呼叫是連坐,不是有人決定拿掉它。
13 張 PR 之間沒有任何東西變紅。

**我自己這個錯值得記下來,因為它跟本 CR 講的是同一個形狀:** 我用當下的 `grep` 結果
推論歷史(「從來沒有」),那是拿快照當歷史 —— 跟 `pits.test.mjs` 拿快照當行為斷言、
跟 `check-cr.test.mjs` 拿 repo 當下狀態當 fixture,是同一件事的三個版本。

## 影響

**這兩條合起來把「開 CR」這條路堵死了**,而 CR 正是每個角色被 scope 擋下時唯一的
合法出口(`scope.json` 的 `_matching.trap` 講的就是不能把出口關掉)。

現在的狀態:

| 你想做的事 | 結果 |
|---|---|
| 開一份 CR | `check-cr.test.mjs` 紅 |
| 留第一則坑註解 | `pits.test.mjs` 紅 |
| 兩件一起做(我) | 兩條都紅 |

而 `verify` 全綠是送 PR 的前提。**這份 CR 自己也在這個坑裡** —— 它是一份 proposed
的 CR,所以它所在的分支也是紅的。我因此沒有送 PR,只推了分支。

還有一件事值得記下來:`pendingSummary` 沒接上這件事,**已經造成過一次實際損失**。
CR-012 躺在 main 上等了一輪才被 architect 發現,而當時給出的對策是「下次開 CR
記得口頭講一聲」。那個功能後來做了,但沒有接上輸出 —— 所以那一輪的教訓其實
還沒有真的落地,只是看起來落地了。

## 建議變更

三處,都在 `scripts/`(infra):

**一、把 `pits.test.mjs:91` 改成驗它真正要驗的東西。** 它要擋的是「文件裡的示範被
當成真坑」,那就斷言掃描結果裡沒有任何 `.md`:

```js
test('文件裡的範例沒有被當成真的坑', () => {
  const fromDocs = scanPits().filter((p) => p.file.endsWith('.md'));
  assert.deepEqual(fromDocs, [], `文件不該被掃進來:${JSON.stringify(fromDocs)}`);
});
```

這樣它擋得住原本的假陽性,而且**不會隨著有人開始使用機制而變紅**。
(旁邊那條「掃描出來的東西一律通過形狀檢查」不必動,它本來就是行為斷言。)

**二、把 `pendingSummary()` 接回 `check-cr.mjs` 的輸出,並且讓那條線自己有測試。**

接回去照 `#78` 原本的位置(`warnings.push(pending)`)就行。但**只接回去只修好今天** ——
等這幾份 CR 都被裁決,`proposed.length` 回到 0,那條測試又走進空分支,同一件事可以被
第三次悄悄砍掉而測試照樣綠。

所以測試要改成**用合成的 fixture**:自己造一份 proposed 的 CR、跑 CLI、斷言輸出裡有
那一行,不要依賴 repo 當下剛好有幾份 proposed。

一句可以重複用的判準:**這條測試斷言的是函式,還是那條線?** `pendingSummary()` 的三條
單元測試在被砍掉的 13 張 PR 之間一直是綠的 —— 因為它們測的是函式,而被砍的是線。

**三、順手看一眼還有沒有同形的。** 兩個判準,對應上面兩條:

- 這條斷言會不會因為「有人開始使用這個功能」而變紅?會的話它斷言的是快照,不是行為。
- 這條測試在功能被拿掉的時候會不會紅?不會的話它測的是函式,不是那條線。

我只掃到這兩條,沒有把握是全部。

## 波及範圍

- **infra** —— `scripts/pits.test.mjs`、`scripts/check-cr.mjs`。都是 infra 的路徑。
- **qa** —— 沒有程式要改,但我手上那條分支(e2e 的坑註解記錄 + CR-013)要等這兩處
  修好才送得出 PR。
- **所有角色** —— 修好之前,誰開 CR 誰的 PR 就是紅的。

## 為什麼是 CR 而不是傳訊息

`scripts/` 不在 qa 的可寫範圍,而依 ADR-009,跨 scope 的知識家是 CR ——
訊息不在 repo 裡,對方的 session 一壓縮就沒了。這件事的受眾是「下一個改
`scripts/` 測試的人」,他需要看到的不只是「改這兩行」,是**那個形狀**:
斷言快照與斷言行為的差別,在功能沒被用過的期間看起來一模一樣。

### 我接受那條判準,並且它已經自己證明過一次

> **這條測試斷言的是函式,還是那條線?**

`pendingSummary()` 的三條單元測試在被砍掉的 13 張 PR 之間一直是綠的。這條判準值得
帶著走,但**它跟 CR-014 自己記的另外兩條是同一件事的三個切面**,不該拆開放:

1. 這條斷言會不會因為「有人開始使用這個功能」而變紅?會 → 斷言的是快照。
2. 這條測試在功能被拿掉的時候會不會紅?不會 → 測的是函式,不是線。
3. (qa 的自我更正)拿 `grep` 的當下結果推論歷史 → 拿快照當歷史。

三條的共同形狀是**拿當下的狀態當前提**。歸檔在這份 CR 裡即可,不升級成 ADR ——
依 ADR-009 的門檻,它是工具與測試的寫法問題,受眾是「下一個改 `scripts/` 測試的人」,
而 #110 已經把它寫進 `agent-workflow` skill §5 了,那正是他會看到的地方。

### 一筆要記的帳:這個狀態欄說了謊 9 個多小時

狀態欄直到本次裁決之前都還是 `proposed`。**宣稱在 commit message 裡,紀錄不在 repo 裡**
—— 這正是 ADR-009:164「訊息可以用來通知,不能用來保存」的又一個實例,只是這次載體是
commit message 而不是 session 訊息。

後果是 `check:cr` 那行提醒一直在響,而響的原因不是「真的有人在等裁決」,是資料在說謊。
ADR-007 把 `tasks.yaml` 的 `status` 拆掉,理由就是存起來的狀態會漂移;CR 的狀態沒辦法
被推導(裁決是人的決定,不是資料的函數),所以它只能存 —— **那就更需要有人負責讓它
不說謊,而那個人是我。這一次是我漏的。**
