# CR-014: 兩個機制在「第一次真的被用到」的那一刻才紅 —— 而現在就是那一刻

- **提出者**: qa
- **狀態**: proposed
- **阻擋任務**: 無

> 不阻擋任務,但**擋住每一張 PR**:現在任何人開一份 CR、或留下第一則坑註解,
> `pnpm verify` 都會紅在 `scripts/*.test.mjs`。包括這一份 CR 自己。

## 問題

`scripts/` 裡有兩條測試,它們斷言的是**「這個 repo 今天還沒有人用過這個機制」**,
而不是機制的行為。兩條都在第一次真的被用到時變紅。

我這一輪同時觸發了兩條:開了 CR-013,並依 ADR-009 在 `e2e/server.ts` 留下第一則
坑註解。兩件都是這兩個機制**被設計出來就是要人做的事**。

### 一、`pits.test.mjs:91` —— 斷言「repo 裡沒有坑」

```js
test('現況掃描是乾淨的 —— 文件裡的範例沒有被當成真的坑', () => {
  const pits = scanPits();
  assert.deepEqual(pits, [], `不該有:${JSON.stringify(pits)}`);
});
```

**意圖是對的**:它要擋的是「ADR-009 與 AGENTS.md 裡的示範標記被算成真的坑」那個
假陽性。但寫出來的斷言是「掃描結果是空的」—— 這兩件事只在**還沒有任何真坑**的時候
等價。第一則真的坑註解一寫,它就紅:

```
不該有:[{"file":"e2e/server.ts","line":92,"role":"qa",...}]
```

諷刺的地方是:這條測試守的機制,它的價值**完全來自於有人會去用它**,
而它的斷言說「沒有人用過」。

### 二、`check-cr.test.mjs:127` —— 一條一直空過的接線測試

這條寫得很好,它刻意不寫死數字:

```js
// 不寫死「現在有幾份 proposed」—— 那會讓這條測試在下一張 CR 開出來時就紅,
// 而它要驗的是「接線有沒有接上」,不是 repo 今天的狀態。
```

但它有兩個分支,而**過去一直走的是空的那一支**:

```js
if (proposed.length === 0) {
  assert.doesNotMatch(out, /仍為 proposed/);   // ← 一直是這一支
} else {
  assert.match(out, new RegExp(`${proposed.length} 份 CR 仍為 proposed,...`));
}
```

在 CR-013 之前,所有 CR 都是 accepted,`proposed.length === 0`,測試**恆真通過**。
CR-013 讓它第一次走進另一支,然後抓到了它本來就要抓的東西:

```
$ grep -n pendingSummary scripts/check-cr.mjs
109:export function pendingSummary(crs) {
```

**`pendingSummary()` 定義了、export 了、有三條單元測試,但 CLI 從來沒有呼叫它。**
`check-cr.mjs` 的輸出裡沒有那一行。這正是那條接線測試存在的理由,它做對了 ——
只是它等了一份 proposed 的 CR 才等到機會。

## 影響

**這兩條合起來把「開 CR」這條路堵死了**,而 CR 正是每個角色被 scope 擋下時唯一的
合法出口(`scope.json` 的 `_matching.trap` 講的就是不能把出口關掉)。

現在的狀態:

| 你想做的事 | 結果 |
|---|---|
| 開一份 CR | `check-cr.test.mjs` 紅 |
| 留第一則坑註解 | `pits.test.mjs` 紅 |
| 兩件一起做(我) | 兩條都紅 |

而 `verify` 全綠是送 PR 的前提。**這份 CR 自己也在這個坑裡** —— 它是一份 proposed
的 CR,所以它所在的分支也是紅的。我因此沒有送 PR,只推了分支。

還有一件事值得記下來:`pendingSummary` 沒接上這件事,**已經造成過一次實際損失**。
CR-012 躺在 main 上等了一輪才被 architect 發現,而當時給出的對策是「下次開 CR
記得口頭講一聲」。那個功能後來做了,但沒有接上輸出 —— 所以那一輪的教訓其實
還沒有真的落地,只是看起來落地了。

## 建議變更

三處,都在 `scripts/`(infra):

**一、把 `pits.test.mjs:91` 改成驗它真正要驗的東西。** 它要擋的是「文件裡的示範被
當成真坑」,那就斷言掃描結果裡沒有任何 `.md`:

```js
test('文件裡的範例沒有被當成真的坑', () => {
  const fromDocs = scanPits().filter((p) => p.file.endsWith('.md'));
  assert.deepEqual(fromDocs, [], `文件不該被掃進來:${JSON.stringify(fromDocs)}`);
});
```

這樣它擋得住原本的假陽性,而且**不會隨著有人開始使用機制而變紅**。
(旁邊那條「掃描出來的東西一律通過形狀檢查」不必動,它本來就是行為斷言。)

**二、把 `pendingSummary()` 接進 `check-cr.mjs` 的輸出。** 位置建議在 CR 清單之後、
`✅ CR 與 tasks.yaml 一致` 之前,與 `warnings` 那段同層。

**三、順手看一眼還有沒有同形的。** 判準是:**這條斷言會不會因為「有人開始使用這個
功能」而變紅?** 會的話它斷言的是快照,不是行為。我只掃到這兩條,沒有把握是全部。

## 波及範圍

- **infra** —— `scripts/pits.test.mjs`、`scripts/check-cr.mjs`。都是 infra 的路徑。
- **qa** —— 沒有程式要改,但我手上那條分支(e2e 的坑註解記錄 + CR-013)要等這兩處
  修好才送得出 PR。
- **所有角色** —— 修好之前,誰開 CR 誰的 PR 就是紅的。

## 為什麼是 CR 而不是傳訊息

`scripts/` 不在 qa 的可寫範圍,而依 ADR-009,跨 scope 的知識家是 CR ——
訊息不在 repo 裡,對方的 session 一壓縮就沒了。這件事的受眾是「下一個改
`scripts/` 測試的人」,他需要看到的不只是「改這兩行」,是**那個形狀**:
斷言快照與斷言行為的差別,在功能沒被用過的期間看起來一模一樣。
