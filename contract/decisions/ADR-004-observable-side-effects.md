# ADR-004: 副作用要驗收,就得在 contract 上留一個可觀察面

- **狀態**: accepted
- **日期**: 2026-09-01
- **來源**: TASK-005(專案負責人通知)—— 交辦前檢查驗收條件時發現它做不到 `done`

## 脈絡

TASK-005 的兩條 AC 都是 `verified_by: e2e`:

> AC-008 專案狀態異動時,寄出通知至 `ownerEmail`
> AC-009 `ownerEmail` 未設定時略過通知,不得報錯

qa 只有 HTTP,而這兩條在當時的 contract 下**一條都驗不了**。兩個洞:

1. **`ownerEmail` 沒有寫入路徑。** CR-002 把它加進 `Project` 的**回應**,
   但 `CreateProjectRequest` 只有 `name`、`UpdateProjectRequest` 只有 `status`
   —— 走 API 永遠設不到它,於是 AC-008 的前提無法建立。
2. **「寄出通知」在黑箱裡看不見。** contract 裡沒有任何東西會因為通知寄出
   而改變,所以就算 backend 做完,qa 也寫不出引用 AC-008 的測試,
   `check:ac` 會擋在 `done` 前面。

**這不是 qa 的限制,是 contract 的缺口。** 一條 AC 宣告 `verified_by: e2e`,
就等於宣稱「這件事在 HTTP 上看得見」;看不見的話,那個宣告本身是錯的。

洞 1 是純粹的疏漏(CR-002 只想加欄位,沒想到誰來寫)。洞 2 才是決策。

## 決策

**副作用要能被黑箱驗收,就必須在 contract 上有一個可觀察面 —— 而那個可觀察面
要是資源本身的一部分,不是為了測試而生的出口。**

具體到本案:`Project` 增加唯讀欄位 `lastNotifiedAt`。

```yaml
lastNotifiedAt:
  type: string
  format: date-time
  readOnly: true    # 不出現在任何 request schema,只由狀態異動產生
```

AC 的措辭因此從「內部發生了什麼」改寫成「可觀察的結果」:

| | 原本 | 改後 |
|---|---|---|
| AC-008 | 寄出通知至 ownerEmail | 設有 ownerEmail 的專案狀態異動後,回應的 `lastNotifiedAt` 更新為該次通知時間 |
| AC-009 | 未設定時略過通知,不得報錯 | 未設 ownerEmail 時略過通知,PATCH 仍回 200 且不出現 `lastNotifiedAt` |
| AC-014 | (新增) | 狀態未實際改變時不通知,`lastNotifiedAt` 不變 |

**改的是驗收方式,不是驗收意圖。** 意圖仍然是「該通知的時候通知了」。

### 這個欄位記的是什麼,不記什麼

`lastNotifiedAt` = **成功交付給寄送機制**的時間。不是「對方收到了」,也不是
「對方讀了」—— 那兩件事不在本 API 的能力範圍內,欄位不該假裝它知道。

**寄送的傳輸方式(SMTP / 第三方服務 / 佇列)不寫進 contract。** 那是實作選擇,
歸 backend 與 infra;contract 只講「通知這件事在外部看起來是什麼樣子」。
與 ADR-002、ADR-003 同一條分界線:**工具選型歸 infra,邊界語意歸 contract。**

### 三個一起定死的行為

寫在 `PATCH /projects/{projectId}` 的 description 裡,因為讀 API 的人會在那裡
找答案,不會先去翻 ADR:

1. **狀態沒有真的改變(`active` → `active`)不通知。** 否則一個會重試的 client
   就是一台騷擾負責人的機器,而那也不叫「狀態異動」。這條獨立成 AC-014 ——
   不寫下來的話,它會變成每個實作者各自猜一次的東西。
2. **沒有 `ownerEmail` 就略過,且不是錯誤。** 200,只是沒有 `lastNotifiedAt`。
3. **通知失敗不會讓 PATCH 失敗。** 這支 API 的職責是改狀態,通知是副作用不是
   前提。失敗時 `lastNotifiedAt` 不更新 —— 於是「沒通知成功」一樣看得見。

第 3 條**刻意不設 AC**:黑箱誘發不了寄送失敗。硬要驗就得在 contract 上開一個
注入失敗的開關,那正是下一節否決的東西。它是一條**被記錄但未被機器保證**的
行為,跟 ADR-003 那條「每一項架構決策留一份 ADR」一樣是已知的欠帳。

## 被否決的方案

- **開一個 `GET /notifications` 之類的出口讓測試去讀。** 最直接,也最壞:
  那個端點只為了被測試而存在,卻會變成產品 API 的一部分、被外部 client 依賴、
  以後拿不掉。**為了讓測試看得見而發明一個功能,是拿契約去補測試的債。**
  `lastNotifiedAt` 不一樣 —— 「這個專案的負責人最後一次被通知是什麼時候」
  本來就是這個資源的合理屬性,即使沒有測試也站得住。
- **把 AC-008 改成 `verified_by: manual`。** 便宜、誠實,但用錯了地方。
  CR-006 裁決把 `manual` 保留給**黑箱在架構上打不到**的東西(純畫面的驗收)。
  一個後端副作用不屬於那一類 —— 它打不到只是因為沒人替它設計可觀察面。
  用 `manual` 當退路,等於把「我沒設計」寫成「這件事天生驗不了」。
- **加一個測試專用的 header 或 query(例如 `?dryRun=1` 回傳將要寄的通知)。**
  同第一項的問題,而且更糟:它把測試模式做進正式端點,production 也帶著跑。
- **維持現狀,讓 backend 先做、之後再想怎麼驗。** 這是最容易發生的一種,
  因為它在當下沒有成本。代價會在 qa 那一步爆開,而那時 backend 已經做完了 ——
  重做的是別人。**驗收方式要在交辦之前就成立**,不是做完再回頭找。

## 代價

- `Project` 多一個欄位,而它的值只有在通知發生過之後才存在。client 必須把它
  當選填處理。
- 「已交付給寄送機制」與「對方收到了」的差別,靠欄位描述傳達,沒有機制保證
  沒有人誤讀。這是文件擋不住的那一類,只能寫清楚。
- 通知失敗那條沒有 AC(見上)。
- 本案只補了「建立時可設 `ownerEmail`」。**改既有專案的 `ownerEmail` 仍然沒有
  路徑** —— 見下節。

## 不在本 ADR 範圍

- **修改既有專案的 `ownerEmail`。** 那要動 `UpdateProjectRequest` 的
  `required: [status]`,而 CR-001 裁決把 `status` 設為必填是刻意的:
  body 只有一個欄位時,選填會讓 `{}` 變成一次「成功但什麼都沒做」的 PATCH。
  一旦多一個可更新欄位,正確的做法是把 `status` 移出 `required` 並改成
  「至少要有一個欄位」的約束 —— 那是另一次設計,而 TASK-005 不需要它。
  **等真的有需求再開 CR**,不要為了對稱先做。
- **通知的重試、去重、退信處理。** 那是一個真正的通知系統該有的東西,
  不是這張任務的範圍。真要做的時候,它會需要自己的 ADR,而且大概會讓
  `lastNotifiedAt` 這個單一欄位不敷使用 —— 那時再換,不要現在先建一個
  用不到的結構。
- **寄送的傳輸方式。** 歸 backend / infra,見上。
