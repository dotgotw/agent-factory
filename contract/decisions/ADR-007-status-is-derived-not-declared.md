# ADR-007: 帶保證的狀態用算的,帶意圖的狀態不放進 contract

- **狀態**: accepted
- **日期**: 2026-09-02
- **來源**: ADR-005 的「不在本 ADR 範圍」列了這一條;動機是 87 張合併 PR 裡有 9 張內容只有 `contract/tasks.yaml` 的狀態欄位

## 脈絡

`tasks.yaml` 的 `status` 有五個值,但它們不是同一種東西:

| 值 | 性質 | 誰知道它是真的 |
|---|---|---|
| `done` | **保證** —— 每條 AC 都有證據 | `check:ac` 已經在算 |
| `blocked` | **保證** —— 有一份 proposed 的 CR 擋著 | `check:cr` 已經在對照 |
| `todo` / `in_progress` / `review` | **意圖** —— 誰打算做、做到哪 | 只有寫的人 |

前兩個由機器算得出來,卻是用手寫的;而寫它們的只有 architect,因為 `contract/`
只有 architect 能寫。結果是 **87 張合併 PR 裡有 9 張(超過十分之一)內容只有
一個狀態欄位**,每一張都走完整的 PR + CODEOWNERS 流程。

方向也是反的。今天 `check-ac.mjs:222` 是

```js
if (task.status === 'done' && !hit) { /* 紅 */ }
```

**用紅燈去追一個人手寫的欄位** —— 先宣告 done,再由檢查確認你沒有說謊。
把高頻率、低風險的訊號(狀態)放進最低頻率、最高風險的地方(contract/、
單一角色、人類 review),是這個安排的根因。

## 決策

**`tasks.yaml` 拿掉 `status` 欄位。**

- **`done` 用算的**:一張任務的每一條 AC 都有證據就是 done。`e2e` 的證據是
  測試裡出現該 AC 編號,`manual` 的證據是合格的 `verified_record`(CR-011)。
- **`blocked` 用算的**:有一份 `proposed` 的 CR 指名它就是 blocked。
- **`todo` / `in_progress` / `review` 不進 contract。** 它們是排程事實,不是
  契約事實 —— contract 的職責是「什麼條件成立才算完成」,不是「誰現在正在打字」。

`pnpm tasks` 顯示算出來的狀態,而且比原本的五個值更有資訊:

```
TASK-012  open (2/3 AC)   backend
TASK-013  blocked         backend   ← CR-014 proposed
TASK-014  done            qa
```

`open (2/3 AC)` 表達的正是原本 `review` 想表達的東西,而且它是量出來的。

### 一定要一起做的事:退步必須是紅的

**這是本決策唯一的陷阱,漏掉它就是淨損失。**

今天「done 的任務掉了測試」會紅(`check-ac.mjs:222`)。改成推導之後,同一件事
會讓那張任務**安靜地從 done 變回 open** —— 沒有人會知道,除非剛好有人去看。
把一個紅燈換成一個無聲的狀態變化,方向跟這個 repo 的每一條規則都相反。

所以推導必須配一個比較基準:

> `check:ac` 比對「本次算出來的 done 集合」與「`origin/main` 上算出來的 done
> 集合」。**在 main 是 done、在這個分支不是 —— 紅。**

不需要新檔案,用 git 就夠(`git show origin/main:contract/tasks.yaml` 與該版本的
`e2e/`)。形狀跟 CR-011 的 `commit` 欄位一樣:拿一個過去的版本當基準,差異才是訊號。

要讓一張任務**合法地**退出 done,就得動它的 AC —— 那是 contract 變更,本來就
該被看見。

### 連帶消失的檢查

`check:cr` 現在有一條「任務標成 blocked,但它引用的 CR 已經 accepted / rejected」
的漂移檢查。推導之後**這個錯誤類別由構造消失**:blocked 就是 CR 的函數,不可能
不一致。那條檢查連同它的錯誤訊息一起刪掉,不是留著空跑。

## 理由

**ADR-002 已經回答過同一個問題。** 那份決策說 `generated/` 不是誰的財產,
**它是一個函數**;`scope.json` 把「函數的輸出」寫成「某人的財產」是一個類別錯誤,
而修法是把描述改對,不是給那個人開例外。

`status: done` 是同一個類別錯誤:**它是「這張任務的 AC 有沒有證據」這個函數的輸出**,
只是在證據還很少的時候,手寫它剛好無害。9 張 PR 是這個錯誤開始收費的證據。

副作用同樣重要:`done` 從「一個人的宣告,再由檢查驗證它沒說謊」變成
**「一個算出來的事實,想造假就得先偽造證據」**。CR-006 裁決當初把 TASK-003 退回
`review` 是為了區分「有人覺得做完了」與「驗過了」—— 推導把那個區分變成不可能混淆,
比當初的做法更徹底。

## 代價

- **看不到「誰正在做」了。** 但那個訊號本來就有更可信的來源:**一張開著的、掛著
  `agent:<role>` label 的 PR**。手寫的 `in_progress` 是一份需要有人記得更新的副本,
  而它從來沒有被任何東西驗證過。
- **推導要跑 git。** 兩個 job 現在都是 `fetch-depth: 0`;改成淺 clone 會讓退步偵測
  從「抓得到」變成「抓不到」而不會紅 —— 又一個靜默降級,值得在腳本註解裡留一句。
  (同 CR-011 裁決對 `commit` 欄位的那句提醒。)
- **第一次算會慢一點**,因為要多讀一個 git 版本。這個規模無感。
- **`--status` 這個查詢旗標的合法值變了**,而它是五個角色依賴的 CLI 介面。
  改它的 PR 描述要寫清楚(ADR-005 的代價那節)。

## 被否決的方案

- **只把 `done` 改成推導,保留其餘四個值。** 少一半的收益,而且留下一個
  「有些狀態是算的、有些是寫的」的混合模型 —— 讀的人每次都要先想這個是哪一種。
- **把 `status` 移出 `contract/`,讓 owner 角色自己寫。** 表面上解決了瓶頸,
  實際上是讓被約束的角色宣告自己的完成度 —— ADR-003 的不變式講的就是這件事。
  而且它沒有回答「為什麼一個算得出來的東西要用寫的」。
- **`in_progress` 從開著的 PR 推導。** 技術上做得到(查 label 與 base),但它把
  `check:ac` 綁到 GitHub API 上,離線就跑不動,而收益只是一個看板欄位。
  **不做,而且是刻意不做** —— 這條線要畫在「證據在 repo 裡」。
- **維持現狀,忍受 9 張 PR。** 這是最容易的選項,而它的成本會隨任務數線性成長。
  ADR-005 已經量過同一類的成長:骨架要拿來開新專案,現在便宜的事以後不便宜。

## 落地順序

必須在 infra 的三欄位驗證(`status` / `owner` / `depends_on`)之後,理由是那張
仍然有效 —— `owner` 與 `depends_on` 的驗證跟本決策無關,而且 `owner` 打錯會靜默
關掉 `verified_record` 的過期偵測。

1. **infra** —— 三欄位驗證(進行中,`status` 那條做完即可作廢)
2. **infra** —— `check:ac` 改成推導 + 退步比對;`check:cr` 刪掉 blocked 漂移檢查;
   `pnpm tasks` 顯示算出來的狀態
3. **architect** —— `tasks.yaml` 拿掉 11 個 `status:` 欄位與檔頭的說明

第 2 步與第 3 步之間 main 會短暫有一個「沒有人讀的 `status` 欄位」,那是無害的;
反過來(先刪欄位)會讓 `check:ac` 當場失去輸入。
