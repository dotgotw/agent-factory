# ADR-009: 知識住在「下一個人會再踩的地方」

- **狀態**: accepted
- **日期**: 2026-09-02
- **來源**: 「角色在任務過程中發現坑,該怎麼處理」—— 這個問題目前每次都是臨時裁決

## 脈絡

這個 repo 已經有七種存放知識的地方,而且它們都在被用:

```
scripts/ 的註解    743 行 / 3,278 行 = 24%
ADR                8 份
CR                 12 份
README             268 行
AGENTS.md × 5      220 行
PR 描述 / commit    ——(在 GitHub,不在 repo 裡)
程式與測試的註解    ——
```

**問題不是缺地方,是沒有寫下該用哪一個。** 今天唯一一條相關指引是

```
backend/AGENTS.md:19   發現 contract 有問題時不要自己改,開 CR 並停下該任務
```

只涵蓋「contract 錯了」,而且只有五份 AGENTS.md 裡的一份有。其餘情況每次都是
臨時判斷 —— 而「每次都要問架構師放哪裡」本身就是規則沒寫下來的症狀。

## 決策

> **知識住在「下一個人會再踩到它的地方」。**

**三問決定家在哪。** 三問是主規則,對每一種家都適用;底下另外兩節
(「為什麼這一條不等第二個實例」、「特例:CR 裁決之後」)是三問的補充,
而「ADR 的門檻」**只在候選的家是 ADR 時才出場** —— 它不是第四問。

### 第一問:下一個人會不會在同樣的地方再踩一次?

**不會 → 寫進 PR 描述,結束。** 一次性的事不值得建檔;建了會稀釋真正該讀的東西。
這一問先問,是因為它擋掉大部分的東西。

### 第二問:他再踩的時候,眼睛在看什麼?

| 他正在做什麼 | 家 |
|---|---|
| 改那支腳本 | 腳本檔頭 / 那一行的註解 |
| 寫或讀測試 | 測試裡的註解 |
| 按合併鍵 | `README.md` |
| 開工的第一分鐘 | 該角色的 `AGENTS.md` |
| **盯著一個紅燈** | **那則錯誤訊息本身**(見下方補充) |
| 寫下一條規則 | ADR |
| 修不掉,要別人動手 | CR |

**踩到的地方不在自己的 scope 裡時,家是 CR。** 例如 qa 發現 backend 的某個行為有坑
—— qa 寫不到 `backend/src/`,而知識該住在 backend 下次會看到的地方。CR 是唯一能讓
它跨界落地的路,而且它會被裁決、被歸檔。**用 session 之間的訊息通知對方不算落地**:
訊息不在 repo 裡,對方的 session 一壓縮就沒了。

### 第三問:那份東西會不會在那一刻出現在他眼前?

選對書、但書沒被打開,跟放錯書架的結果一樣。前兩問只決定**放哪裡**,不決定
**會不會被端出來** —— 這個 repo 的家分成三層,差別在誰主動:

| 層 | 管道 | 誰主動 |
|---|---|---|
| 無條件推送 | `CLAUDE.md` 的 `@AGENTS.md`;SessionStart hook 跑的 `pnpm role` | 系統。每個 session 都會看到 |
| 條件推送 | skill 的 `description` —— 它決定那份 skill 什麼時候被載入 | 系統,但條件寫錯就等於沒放 |
| 拉取 | README、ADR、CR、程式與測試的註解 | 讀的人得自己走過去 |

**放在拉取層的東西,如果它的受眾不會主動走過去,就需要一個推送層的指標。**

坑註解就是這個形狀:內容在程式旁邊(拉取),而開場那一行計數是推送的指標。
本 ADR 補充裡「開場只印固定長度」那個決定,現在有了一般化的理由 ——
**無條件推送的預算是所有 session 共同支付的,所以那一層只能放常數長度的東西**,
細節留在拉取層。

條件推送最容易出錯,因為它看起來已經放好了。實例:探針衛生那節放進
`agent-workflow` 的 skill,受眾是「正在跑探針、準備回報數字的 agent」——
但那份 skill 的觸發條件當時只寫了「開工、被擋、送 PR、CI 紅燈」,跑探針不在裡面。
**內容放對了文件,而那份文件在需要它的時候不會被打開。**

### 為什麼這一條不等第二個實例

本 ADR 自己規定「一個實例還不夠,兩個才看得出形狀」。這一條只有一個實例,
仍然寫進來,因為那條門檻管的是**「這是不是一個值得記的形狀」**;
這裡的形狀(ADR-009)已經記下來了,而這一條是**「已記下的規則少了一步」**。
規則被用了一次就給出不完整的答案,那不需要第二次確認。

### 補充:盯著紅燈的人,家是那則錯誤訊息

第二問的表原本沒有這一列,但「理由」那節早就用過它 —— `status` 欄位不得存在,
「對送 PR 撞到紅燈的人是那句錯誤訊息」。venue 一直都在,缺的是**觸發條件**:
你怎麼知道自己這則訊息就是需要多一句話的那則?

> **照這則錯誤訊息去查,查到的地方會有東西可修嗎?**
> **沒有 → 訊息缺一句話。**

#### 三個實例,都是同一週撞到的

| 失敗 | 訊息把人推去查 | 那裡的實況 |
|---|---|---|
| CR-013:`before()` 綁不到 port | `AC-008` 的斷言(六條 AC 一起紅,`fail=0`) | 健康 |
| CR-017:殘留的 boundary fixture | workspace 連結、`tsconfig` 的 `paths`、`pnpm install` | 健康 |
| `check-drift` 紅在未 commit 的手寫改動 | `sync-agents.mjs`(症狀像生成器壞了) | 健康 |

**三則訊息都沒有說謊。** tsc 真的解析不到那個模組,AC-008 真的沒跑完,工作區真的
跟 HEAD 不一樣。它們報的是**真實的近因**,而近因所在的那個元件是健康的 ——
所以讀的人照著查,保證查不到東西。

#### 修法可以一般化,因為知識本來就已經存在

三個案例裡,系統中都**已經有某一段知道真正的原因**:

- `check-boundaries.mjs` 有一段把兩種可能和確認方式都寫清楚的診斷 —— 它排在 typecheck 後面
- `check-drift.sh` 知道自己比對的是工作區與 HEAD —— 它沒有在訊息裡說
- `e2e/server.ts` 的檔頭寫過那個窗口「這不是零」—— 那句話不在失敗的輸出裡

> **讓已經知道真正原因的那一段先說話,而不是讓讀的人自己走回去。**

三次的修法都是這個:#114 把 `check:boundaries` 排到 `typecheck` 之前(讓好的診斷跑得到)、
`check-drift.sh` 的訊息多講一種可能、CR-013 直接消除近因並在檔頭留下形狀。

#### 為什麼是錯誤訊息,而不是把這些寫進 README

依第三問的三層看,錯誤訊息是**推送**,而且是唯一一種**按需付費**的推送:

| | 誰付這個預算 |
|---|---|
| `pnpm role` 開場那幾行 | **所有 session,每一次**。所以只能放常數長度 |
| **錯誤訊息** | **只有撞到的那個人,只在撞到的那一次** |

這就是為什麼開場那一層要克制、而這一層不必。多寫兩句話給一個**已經卡住**的人,
成本是零 —— 他本來就要花時間,而那兩句話決定他花在對的地方還是錯的地方。

反過來說,把這些知識放進 `README` 或 ADR 是**拉取層**,而撞到紅燈的人不會先去翻。
內容放對了文件,而那份文件在需要它的時候不會被打開 —— 跟第三問那個 skill
`description` 的實例是同一個錯。

#### 一個相鄰、但不歸這裡的形狀

skill §4 的合併監看片段:`gh` 查詢失敗時回傳空字串,而 `[ "" != "OPEN" ]` 為真,
於是迴圈提早結束、exit 0、任務通知說 completed。

它跟上面三個像:讀的人得到一個確信的錯誤結論。但**它不是「訊息指錯地方」,
是「不知道被印成一個確定的答案」** —— 終止條件把「查不到」和「狀態變了」混成同一件事。
那條規則的家在 `agent-workflow` skill §5(「問不出答案 ≠ 答案是否定的」),infra 已經
放在那裡了。

寫進來是為了畫界線:**這一條管的是「訊息指向哪裡」,不管「訊息該不該被當成答案」。**
兩者都會讓人走錯路,但修法不同 —— 前者補一句話,後者改判斷條件。

### 特例:CR 裁決之後,理由要移植

`change-requests/` 是唯一一種**知識一開始就在錯的地方**的家。CR 由被擋住的人寫、
由 architect 裁決,然後躺在一個沒有人會逛的目錄裡 —— 而裁決的理由往往是這個 repo
最值得留下的東西。

量過一次(12 份 accepted 的 CR,看有多少從程式、測試、腳本、ADR、contract 指過去):

```
CR-004   11 個活路   9 個 e2e spec + server.ts + pits.mjs
CR-012   10 個活路   backend/src/errors.ts、openapi.yaml、3 個 spec
CR-006    8 個活路   ci.yml、check-ac.mjs、tasks.yaml、2 份 ADR
...
CR-007    0 個活路   只有另外兩份 CR 引用它
```

**11 份有活路,1 份沒有。** CR-007 講的是 `.claude/settings.local.json` 沒被
`.gitignore` 忽略 —— 而保護只活在維護者的全域設定裡,所以在他機器上永遠是綠的、
永遠不會被發現。裁決 accepted,修法落在:

```
.gitignore:5   .claude/settings.local.json
```

一行,沒有註解,README 也沒提。**規則活下來了,理由沒有。** 哪天有人整理
`.gitignore`,那行看起來就是一條沒來由的設定,而它擋的東西(整個 repo 的 session
拿到同一個 `AGENT_ROLE`、角色系統靜默退化、CI 不會抱怨)寫在一份沒有任何東西指過去
的檔案裡。

所以:

> **裁決一份 CR 的時候,一併決定它的理由要不要移植、移植到哪。**
> 判準就是上面三問,受眾是「下一個會踩到這條規則的人」。

CR 本身之後是**檔案庫**:`check:cr` 每次都讀它的狀態欄做一致性比對,那是機器的用途;
對 agent 而言,**指標才是它的生命**。

**不為此加檢查。** 「每份 accepted 的 CR 都必須有活路引用」會製造假指標 ——
有些 CR 本來就該變成純歷史(問題解決了、理由不需要再被讀),硬湊一個引用比沒有更糟,
因為它看起來像資訊。這一條靠裁決當下的判斷,不靠事後稽核。

### ADR 的門檻另外算(只在候選的家是 ADR 時才出場)

**這一節不參與「家在哪」的決定 —— 那是三問的工作。** 三問先指出家在哪;
只有當它指向 ADR 時,才輪到下面兩個條件決定「值不值得寫成一份 ADR」。

拿它去做別的決定會得到錯的答案,而且實際發生過三次:用「兩個實例」去判斷要不要寫進
skill(那是 ADR 的門檻,skill 的門檻是「下一個人會不會再踩」)、用「是不是我們造成的
形狀」去替一個 skill 條目找不進 ADR 的理由(那條在該案例其實是通過的,正確的理由是
受眾)、以及用它推翻第二問已經給出的答案。**閘門被拿去做主規則的工作,三次都是同一格。**

不是所有值得記的都是 ADR。兩個條件同時成立才是:

1. **是我們自己造成的形狀**,不是工具的行為。
   工具的行為(例如 squash merge 會讓疊放的分支需要 rebase)家在 README ——
   它的受眾是「準備按合併鍵的人」,不是「準備寫規則的人」。
2. **重複出現過。** 一個實例還不夠,兩個才看得出形狀。
   ADR-006 是同一條原則被套用六次之後才寫下來的;ADR-008 是一輪撞到三個同形的死結。

## 缺口:第一個實例沒有家

「兩個實例才升級」意味著第一個必須先活下來。而今天它只能待在 PR 描述裡 ——
**那不在 repo 裡**:clone 下來讀不到、`grep` 不到、離線看不到。等第二次踩到,
沒有人記得第一次。

**修法:第一個實例就地留註解,而且留的時候寫出「我預期誰會再踩」。**
第二次要寫同一句話的時候,那就是升級的訊號 —— 觸發器是**你發現自己在複製貼上
同一段註解**。

**這一段沒有機制,靠人注意。** 不假裝它有。硬做一個「偵測相似註解」的檢查,
假警報會比它擋到的多,而噪音的下場這個 repo 已經寫過三次:被人繞掉。
這跟 ADR-006 那條「每一項架構決策留一份 ADR」一樣,是一筆明說的欠帳。

## 補充:第一個實例的標記形式(infra 提出,採用並修改一處)

上面把「第一個實例沒有家」寫成靠人注意的欠帳,理由是我想不出一個不會退化成 TODO
的標記形式。infra 提出了一個,而且它答對了我沒問對的那一題:

> **標記詞會退化成墓地的原因不是「標記」,是「沒有消費者」。**
> TODO 爛掉是因為寫的時候有人、讀的時候沒有。任何標記只要沒有人固定去看,
> 三個月後都是同一個下場。所以問題不是「用什麼字」,是「誰、什麼時候、為什麼會去讀」。

這個 repo 剛好有一個現成的自動消費者:`pnpm role` 在 SessionStart hook 裡,
**每個 session 開場都會跑,沒有人需要記得**。

### 形式

```
// 坑(下一個踩的人:qa):e2e 的 port 寫死,兩個 session 同時跑會互撞
```

規則一條:**必須指名一個角色**。形狀檢查驗得了這一半(用了標記就得帶一個
`scope.json` 裡存在的角色名),驗不了「這是不是真的坑」—— 那不可判定,不假裝驗。

最強的性質是第三個,它不靠紀律:**噪音會落在被指名的人身上。**
亂標一堆給 qa,qa 每次開 session 都看到,然後來找你。這是自我限制,不是自律。

### 我改一處:開場只印固定長度,細節按需查

infra 原案是開場印出那幾條的內容。**改成開場只印一行計數**,細節用指令查。

理由是 `pnpm role` 現在的輸出是 **10 行、全部常數長度**;坑註解會是第一個沒有上限
的東西,而它出現的位置是**每個 session 都要付、而且注意力最稀缺的那一刻**。
一條坑很有用,二十條就是一面牆,而牆的下場是被跳過 —— 連同它上面那十行一起。

「只印前幾條 + 總數」也不夠:那仍然隨累積變長。**要的是常數。**

### 一個不是坑註解的家:`openapi.yaml` 的 description

infra 在實作時說它「不覺得 openapi 的 description 是坑註解該住的地方」,並把它歸類成
慣例問題。**它是路由問題,所以歸這裡。**

那份文字不是註解 —— 它會原樣流進 `generated/api.ts`(現有 16 處 `@description`),
成為 **API 消費者讀到的文件**。用本 ADR 的第二問檢查:再踩的人是誰?是實作這支
endpoint 的角色,不是讀 API 文件的人。**受眾對不上,所以家不在那裡。**

坑註解的家是實作那一側的程式或測試;`description` 寫的是這支 API 對外承諾什麼。
把內部的坑寫進去,等於把工地圍籬留在交屋的房子裡。

### 陳舊的標記:沒有機制,但擺放讓它比 notes/ 好

坑修掉之後誰刪那行?沒有機制,infra 自己先講了。

不做機制,但有一個結構上的理由讓它不至於失控:**標記就在被修的那段程式旁邊。**
修坑的人正在看那幾行,刪掉它是順手;`notes/` 裡的一則筆記則沒有任何時刻會把
修的人帶到它面前。這正是本 ADR 主規則的同一條推論。

**欠帳因此變窄,不是消失:** 從「第一個實例不在 repo 裡」變成「在 repo 裡、
會被指名的人看到,但沒有人在數它出現幾次,也沒有人保證它還成立」。

### 一個我不接受的宣稱

infra 說這個形式「不能當 TODO 用,因為沒有待辦語意」。**這一條我不買。**
`// 坑(下一個踩的人:backend):這裡的錯誤處理還沒做` 就是一則穿著外套的 TODO,
而且它會被寫出來。命名幫得上忙,但擋不住。

真正擋住它的是上面第三個性質 —— 被指名的人會看到,然後來問你「這是坑還是你沒做完」。
**它靠的是社會成本,不是語意。** 這個差別要寫清楚,否則下一個人會以為形式本身有保證。

## 理由

**受眾決定家,不是主題決定家。** 同一件事對不同的人是不同的東西:`status` 欄位
不得存在,對寫規則的人是 ADR-007,對改 `check-ac.mjs` 的人是那支腳本的檔頭註解,
對送 PR 撞到紅燈的人是那句錯誤訊息。三份都寫,不是重複 —— 是三個受眾。

反過來說,把所有東西堆進同一份文件的代價是**每個讀者都得先分辨哪幾段跟自己有關**。
這個 repo 的 `AGENTS.md` 開頭就寫著「本檔是目錄,不是知識庫」,說的是同一件事。

## 被否決的方案

- **開一個 `notes/` 或 `learnings/` 目錄收集心得。** 兩個問題:它會變成沒人讀的墓地
  (寫的時候有人,讀的時候沒有,因為沒有人在踩到坑時會想到去翻它);而且**它歸誰?**
  一個沒有擁有者的目錄在這個 repo 是反模式,ADR-002 就是為了修掉這種東西。
- **每個發現都開一張 CR。** CR 是「請求跨界變更」,不是觀察筆記。把觀察塞進 CR 會
  逼 architect 為每一件小事裁決一次,而 CR 的價值正在於它是**被擋下時的出口**,
  不該被日常筆記稀釋。
- **靠 session 之間的訊息傳遞。** 快,但訊息不在 repo 裡,而且對方的 session 一壓縮
  就沒了。訊息可以用來**通知**,不能用來**保存**。
- **一律寫進 ADR。** 8 份 ADR 現在每一份都值得讀,那是因為門檻高。降低門檻的代價
  不是多幾份檔案,是**那個目錄不再值得整份讀**。

## 代價

- **判斷成本落在發現的當下。** 撞到坑的人得先想「誰會再踩、他在看什麼」,
  比直接丟進一個收集箱麻煩。這是刻意的:那一分鐘的判斷,換的是下一個人不必翻墓地。
- **升級沒有機制**,見上。
- **同一件事可能寫三份**(給三種受眾)。看起來像重複,實際上不是 —— 但它確實需要
  三次維護,而其中兩份沒有任何檢查在守。
