# ADR-006: API 不得靜默接受或吞掉它沒有宣告的東西

- **狀態**: accepted
- **日期**: 2026-09-01
- **來源**: 這條規則被套用了六次才被寫下來 —— 本 ADR 是補記,不是新決策

## 脈絡

從 CR-001 到 TASK-011,同一條理由出現了六次,每次都寫在不同的地方
(一次在 CR 裁決、四次在 `tasks.yaml` 的註解、一次在 `openapi.yaml` 的
description)。沒有人把它寫成一條規則,於是每一次都像是獨立的判斷。

| # | 情況 | 靜默的行為 | 改成 |
|---|---|---|---|
| CR-001 | `PATCH {}` | 200,什麼都沒做 | `status` 必填 → 400 |
| TASK-007 | `?status=bogus` | 200 + 空列表 | 400 `VALIDATION_ERROR` |
| TASK-008 | body 有未定義欄位 | 200/201,該欄位被忽略 | 400,訊息點名欄位 |
| TASK-009 | 語法錯誤的 JSON | 400 但 body 是 HTML | 400 + `Error` schema |
| TASK-010 | body 超過上限 | 413 但 body 是 HTML | 413 + `PAYLOAD_TOO_LARGE` |
| TASK-011 | `/Projects`、`/projects/` | 200,契約沒宣告過這些路徑 | 404 |

前五列的症狀是同一句話:**「成功了,但你要的事沒發生」**,而 client 沒有任何
辦法知道。第六列是它的鏡像:**「成功了,但你依賴的東西沒有人保證過」** ——
那片相容面沒有寫進契約,卻已經有人能用,哪天收掉就是無預警的破壞。

## 決策

> **API 對它沒有宣告的輸入,要明確失敗;對它沒有宣告的路徑,不要提供服務。
> 兩者都不可以靜默通過。**

推論三條,實作時照這個順序想:

1. **未宣告的輸入 → 4xx,而且 body 是 `Error` schema。** 「回了正確的狀態碼但
   body 是 HTML」不算做到 —— 那個回應的形狀契約沒宣告過,client 解析不了。
2. **錯誤的形狀是全域的,不是每支 endpoint 各自決定的。** `Error.code` 是
   enum(CR-012),新增值必須是一次看得見的 contract 變更。
3. **不要用一個籠統的 code 蓋掉不同的失敗。** 把「你的 body 有 200KB」壓成
   `VALIDATION_ERROR`,等於叫 client 去改欄位,而它該做的是少送一點。

## 理由

**靜默的錯誤來源比明確的失敗貴。** 明確的失敗在開發時就被發現一次;靜默的
失敗會活到 production,而且它的症狀出現在離原因很遠的地方 —— 使用者說「我
改了負責人但沒有生效」,而 log 裡是一片 200。

第二個理由跟這個 repo 的整體設計一致:**它把「悄悄」變成「吵鬧」。**
`check:drift` 抓生成物悄悄過期,`check:ac` 抓 AC 悄悄失去測試,ADR-003 抓依賴
邊界悄悄消失。API 靜默吞掉未宣告的輸入是同一個形狀,只是發生在執行期。

## 邊界:契約管到哪裡為止

TASK-010 問到了這條線的另一半,答案是**不採**:

> **契約描述它宣告的操作,不描述未宣告的路徑。**

所以「打到 `/nope` 會發生什麼」不是本規則的範圍 —— 一份契約沒辦法枚舉、
也沒辦法驗證它自己路徑集合的補集。判準是:**413 發生在一個已宣告的操作上,
`/nope` 不是操作。**

要讓「所有錯誤都是 `Error`」變成全 API 的保證,那是 `info.description` 層級的
另一個決定,**不能當成 bug 修進來**。這條寫在 `openapi.yaml` 的
`info.description` 裡,讓界線是讀得到的。

## 代價

- **對 client 更嚴格。** `additionalProperties: false` 讓「新 client 對舊 server
  送新欄位」從被忽略變成 400。這個 repo 前後端同一個 commit 部署,可接受;
  真的出現版本落差的那天,要處理的是部署方式,不是把驗證放寬。
- **每一條都要有 e2e。** negative case 的測試量比 happy path 多,AC-013 到
  AC-018 六條全部是這一類。這是這條規則的實際成本,不是額外的。
- **express 的預設值全部站在反面。** `case sensitive routing`、`strict routing`
  預設 false,`express.json()` 的錯誤走預設 HTML 處理器 —— 換一個框架要重新
  逐項檢查一次,不能假設。

## 被否決的方案

- **寬鬆接受、由 client 自己小心。** 這是 express 的預設,也是六次事故的來源。
- **只修 PATCH 那一半**(TASK-008 提出時的原始範圍)— 只修一半會製造新的
  不一致,而 POST 打錯欄位名的案例同樣真實。
- **為每種失敗開一個新 code。** 另一個極端。`code` 是 client 拿來分支的東西,
  分支太細等於逼 client 處理它不在乎的區別。判準是「client 會不會因此做不同的事」。
