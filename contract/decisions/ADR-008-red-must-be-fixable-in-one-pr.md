# ADR-008: 判紅之前先問「一張 PR 補得完嗎」

- **狀態**: accepted
- **日期**: 2026-09-02
- **來源**: ADR-007 落地時連續撞到三個死結,全部是同一個形狀

## 脈絡

ADR-007 的規格由我寫、infra 實作。字面照做會擋死三條**合法**路徑:

| 動作 | 誰做得到 | 讓它變綠要動什麼 | 誰做得到 |
|---|---|---|---|
| 在 done 的任務上新增 AC | architect(`contract/`) | 新 AC 的測試 | qa(`e2e/`) |
| 把 AC 從 `manual` 改成 `e2e` | architect(`contract/`) | 那條 e2e 測試 | qa(`e2e/`) |
| 對 done 的任務開 proposed CR | 任何人(`change-requests/`) | 沒有東西補得了 | — |

三個都不是「慢」,是**解不開**:CI 要求恰好一個 `agent:*` label,而讓 PR 變綠所需
的檔案跨了兩個角色。送出的人只能眼睜睜看著紅燈,沒有任何一條合法路徑通往綠。

**三個都是規格寫「紅」寫出來的,而且三個都是我寫的。** 讀規格讀不出來 ——
它們只在兩個角色的邊界上顯形。

## 決策

> **任何一條會判紅的規則,寫進規格之前先問:
> 讓它變綠所需要動的檔案,能不能由單一角色在一張 PR 裡動完?**
>
> **不能 → 那條規則會製造死結。** 改成 ⚠️,或在規格裡寫出明確的多張 PR 補救路徑。
> 兩者擇一,不可以留著紅燈假裝有人補得起來。

判準只看**補救**,不看**成因**。成因是誰不重要 —— 重要的是紅燈出現之後,有沒有
一條合法路徑通往綠。

### 為什麼不是「同一個角色」,也不是「同一個 scope」

這條規則有三個版本,前兩個都不夠準:

- **「補救的人跟造成的人是不是同一個角色」**(我的第一版)—— 把成因扯進來了。
  成因與補救不同人也可能沒事,只要補救那一邊自己動得完。
- **「補救所需的檔案是不是在同一個 scope 裡」**(infra 的修正)—— 更接近,但會
  **誤報**。infra 舉的例子是 `scripts/` 與 `.github/` 分屬兩個 scope,可是這個 repo
  裡它們同屬 infra,一張 `agent:infra` 的 PR 兩邊都動得到,CODEOWNERS 的對象也是
  同一個人。scope 不同不等於補不完。
- **「單一角色在一張 PR 裡動得完嗎」**(採用)—— 直接對著真正的約束問:
  `check:scope` 要求恰好一個 `agent:*` label,且全部檔案落在該角色的可寫路徑。
  這是紅燈能不能被消掉的**充要條件**,其餘都是它的代理指標。

### 已經套用它得到的兩種答案

**改成 ⚠️**:退步比對分流(ADR-007 補充)。AC 的**結構**變了(id 集合或
`verified_by`)→ ⚠️,因為補救要跨 `contract/` 與 `e2e/`;只有散文變了 → ❌,
因為補救就是把測試放回去,qa 一張 PR 動得完。

**改成不觸發**:`done` 蓋過 `blocked`。開 CR 的人補不了任何東西,而開 CR 是被擋下
時唯一的合法出口 —— **讓逃生門把 CI 弄紅,是所有死結裡最糟的一種。**

反例(判紅是對的):刪掉 `verified_record`。證據消失本來就該紅,而補救就是把紀錄
放回 `contract/tasks.yaml`,architect 一張 PR 動得完。

## 理由

這個 repo 的紅燈很貴 —— 它擋合併,而且 `main` 不允許是紅的。所以**一條補不起來的
紅燈不是嚴格,是壞掉**:它把一條合法路徑從流程裡刪掉,而刪掉的方式是讓人撞牆,
不是讓人看到公告。

第二個理由是它便宜:這條檢查在**寫規格的時候**做只要想一分鐘,在**實作的時候**
才發現要重寫規格、改實作、補測試、再改一次 ADR。ADR-007 這一輪就付了三次。

## 代價

- **會多出一些 ⚠️。** ⚠️ 比 ❌ 弱,而弱的訊號會被忽略 —— 這是真的代價,不假裝沒有。
  緩解方式是 ⚠️ 的訊息要寫出「這是刻意的、以及什麼情況下它其實是壞事」,
  而不是只說「注意」。
- **判斷需要知道 scope 表。** 寫規格的人得先知道哪些檔案歸誰。這在這個 repo 是
  `scripts/scope.json`,一份查得到的東西,不是默契。
- **它擋不住「三張 PR 才補得完」的路徑**,只擋得住「沒有任何路徑」。後者是死結,
  前者只是麻煩 —— 但麻煩到某個程度也該重新設計,這條規則不負責畫那條線。

## 被否決的方案

- **一律用 ⚠️,不判紅。** 那會讓 `check:ac` 這類檢查退化成公告板。這個 repo 的整套
  設計是把「悄悄」變成「吵鬧」,而最吵的是紅燈。
- **放寬「恰好一個 `agent:*` label」讓跨角色 PR 過。** ADR-002 與 ADR-003 各否決過
  一次同類的提案,理由相同:例外的觸發條件在被約束者手上。
- **靠人記得。** 這一輪三個死結,三個都是規格作者(我)沒想到、實作者用端到端探針
  撞出來的。**記不住不是態度問題,是這種錯誤只在兩個角色的邊界上顯形。**

## 怎麼用

寫任何新檢查、新 AC、新 ADR 條款時,對每一條「→ 紅」問一次:

1. 誰會踩到它?
2. 踩到之後,讓它變綠要動哪些檔案?
3. 那些檔案有沒有落在**同一個角色**的可寫路徑裡?
4. 沒有 → 降級成 ⚠️,或寫出多張 PR 的補救順序。

第 3 步查 `scripts/scope.json`,或直接跑 `pnpm role`。
